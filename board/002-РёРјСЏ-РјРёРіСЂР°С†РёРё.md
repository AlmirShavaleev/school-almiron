## Задание

Файл в ветке называется
`supabase/migrations/20260909174447_school_stats_oldest_pending_and_today.sql`,
а в `schema_migrations` записана версия **`20260909174536`**. Разница
полторы минуты — между записью файла и применением через MCP.

Правило проекта: имя файла миграции в точности равно версии в
`schema_migrations`. Иначе при следующей сверке миграций эта попытается
примениться повторно. Этот же дефект был у §136 месяц назад, так что
случай не единичный — при записи файла бери версию из ответа
`apply_migration`, а не из своих часов.

Переименуй файл в `20260909174536_school_stats_oldest_pending_and_today.sql`.
Содержимое не трогай.

Проверь и назови в отчёте результат:

```sql
select version, name from supabase_migrations.schema_migrations
order by version desc limit 1;
```

Версия должна совпасть с именем файла посимвольно.

Слияние по-прежнему за владельцем — правило не снимаем.

## Ответ оркестратора

**Принято, сверено по факту.** `main` стоит на `c449a84` — владелец слил
ветку повторно, переименование доехало, файла со старым именем в
репозитории нет. Версия в `schema_migrations` и имя файла совпадают.

Урок про порядок записан в карту как правило: **сначала применить
миграцию, прочитать фактическую версию из `schema_migrations`, и только
потом писать файл под этим именем.** Обратный порядок даёт расхождение
при любой задержке — у нас так вышло дважды, у §136 и у §147.

Про `board/` в `git status` — проверил экспериментально, опасение не
подтвердилось. `git add -A` затянет только `board/.gitignore` и
`board/README.md`, и это замысел: регламент доски полезно иметь в
истории. Сами задачи игнорируются правилом `*`, проверка
`git check-ignore` это подтверждает. Переписка в историю не уедет.
