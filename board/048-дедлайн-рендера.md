# 048 · Бюджет рендера — один на работу, а не на каждый файл

**Статус:** новая
**Кому:** облачный агент оркестратора
**Ветка:** `work/ai-render-deadline`, от `origin/main`
**Раздел PROJECT_STATE:** **§196** — номер выдан оркестратором
**Заведено:** 2026-09-17

## Зачем

Нашёл агент §193 и честно записал в отчёт: `RENDER_BUDGET_MS`
отсчитывается заново **на каждый файл** работы, потому что `startedAt`
живёт внутри `renderPdfPages`, а она вызывается на каждый PDF. Работа из
трёх PDF — это до трёх бюджетов подряд, то есть до 4,5 с при жёстком
пределе ~2 с процессорного времени edge-функции. За пределом воркер
убивают с кодом 546, и задача остаётся висеть в `processing` навсегда —
преподаватель смотрит на вечный спиннер (§48).

Сейчас не стреляет: на проде нет ни одной работы больше чем с одним PDF
(8 работ с одним, 65 из фотографий — проверено запросом 16.09). Но это
вопрос времени: ученик, сдающий две части рабочего листа отдельными
файлами, — совершенно нормальный случай. А §193 сделал дыру шире:
бюджет вырос с 1100 до 1500 мс.

## Что сделать

### 1. Дедлайн на работу целиком

Считать бюджет не от начала файла, а от начала рендера **всей работы**:
завести абсолютный момент `deadline = Date.now() + RENDER_BUDGET_MS`
один раз в `collectPages` и передавать его в `renderPdfPages` вместо
того, чтобы каждая заводила свой `startedAt`. Проверка в цикле страниц
сравнивает с этим общим дедлайном.

### 2. Хотя бы одна страница с каждого файла

Правило, которое нельзя потерять при переходе на общий дедлайн: сейчас
цикл гарантирует «хотя бы одну страницу» у каждого файла
(`if (images.length > 0 && …) break`). С общим дедлайном второй файл
рискует не отдать вообще ничего, а это хуже обрезки: работа будет
выглядеть так, будто второго файла не существует.

Поэтому: **первая страница каждого файла рендерится всегда**, даже если
дедлайн уже вышел; дальше — по дедлайну. И если из файла взята не вся
пачка, это по-прежнему уезжает в приписку `skipped` (и, с §189, гасит
балл).

### 3. Ограничение на число файлов

Если файлов в работе много (скажем, восемь PDF по 10 страниц),
«хотя бы одна страница с каждого» само по себе пробьёт лимит. Поэтому:
если PDF-файлов больше, чем можно честно отрендерить (оценивай по
плотности §193 и оставшемуся дедлайну), остальные файлы **не
открываются вовсе** и попадают в `skipped` строкой «файл не проверен:
не хватило времени рендера». Молча пропускать нельзя.

## Границы

- Логику проверки, промпт, сверку вердиктов (§189), панель — не трогать.
- Плотность рендера (§193) не переделывать, только использовать.
- Фотографии рендера не требуют — их путь не трогать.
- Миграций нет. Функцию **не деплоить**.

## Приёмка

- Тесты (чистое — в `findings.ts`, как всё в этой зоне): планировщик
  «сколько файлов и страниц влезает в дедлайн» — три файла по 5 страниц
  при бюджете 1500 мс и цене 109 мс; один файл на 20 страниц; восемь
  файлов (часть не открывается вовсе, все попадают в `skipped`);
  гарантия «первая страница каждого открытого файла».
- В отчёте — арифметика худшего случая: сколько процессорного времени
  максимум может съесть рендер после правки (должно быть меньше 2 с с
  запасом).
- `npx tsc -b > tsc.log 2>&1; echo $?` последним; патч от `origin/main`
  в `../patches/048-ai-render-deadline.patch`; отчёт.
