# 055 · Сколько ученик смотрел видео — начать записывать

**Статус:** новая
**Кому:** облачный агент оркестратора
**Ветка:** `work/video-watch`, от `origin/main`
**Раздел PROJECT_STATE:** **§204** — номер выдан оркестратором
**Заведено:** 2026-09-17

## Зачем

Владельцу нужен отчёт по ученику, и в нём строка «сколько минут смотрел
видео». Оркестратор проверил базу: **такой записи нет нигде** — ни
таблицы, ни колонки, ни одной строки (искал по всем колонкам со словами
watch / seconds / minutes / duration / progress; нашлись только
`lessons.duration_minutes` и `courses.duration_weeks`).
`bunny_video_stats_cache` — сводка для админского экрана «Видео», две
строки, привязки к ученику нет.

Отсюда порядок работ: **запись идёт вперёд отчёта**. Данные копятся
только со дня, когда их начали писать, и каждый день без этой карточки —
день, которого в первом отчёте не будет.

## Решения владельца (приняты оркестратором ночью, владелец спал)

1. Ученику показываем **отметку «просмотрено»**, число минут ему не
   показываем — минуты видит только персонал курса. Отменить это позже
   дёшево, вернуть подростку самооценку после «ты посмотрел 12 минут из
   90» — дорого.
2. Просмотры персонала (преподаватель, куратор, владелец) **не
   считаются**: иначе собственная проверка материала попадёт в
   статистику ученика и курса.
3. Первые данные появятся со дня выкладки. Везде, где показывается
   число, должна стоять подпись «с такого-то числа» — иначе цифра
   выглядит обидно маленькой и ей перестанут верить.

## Главная трудность, скажу сразу

Видео вставлено **iframe'ом** (`TopicMaterialItems.tsx`, строка ~155;
адрес даёт `getVideoEmbedUrl` — Bunny, YouTube, Vimeo). Iframe чужого
происхождения, обычные события плеера оттуда не видны. Единственный
честный путь — протокол **player.js** поверх `postMessage`, который
плеер Bunny поддерживает: страница шлёт в iframe
`{ context: 'player.js', version: '0.0.4', method: 'addEventListener',
value: 'timeupdate', listener: '…' }` и получает обратно сообщения с
текущей позицией и длительностью.

**В этой карточке — только Bunny.** Там лежат собственные видео школы,
ради них всё и делается. Для YouTube и Vimeo оставь шов (свой модуль
с понятной границей), но не реализуй — это отдельная карточка.

**Чего ты не сможешь проверить, и это нормально.** До боевого Bunny из
облака не дотянуться, поэтому точную форму сообщений плеера подтвердит
только владелец на проде. Пиши приёмник **оборонительно**: сообщения,
которые не похожи на ожидаемые, молча игнорируются. И главное правило
деградации: **если события не приходят — не записываем ничего.**
Никаких «раз вкладка открыта, значит смотрит»: выдуманные минуты хуже
отсутствующих, потому что по ним начнут принимать решения. В отчёте
честно напиши, что этот кусок проверен только на заглушке.

## Что сделать

### 1. Миграция `supabase/migrations/PENDING_204.sql` (не применять)

```
video_watch_daily
  student_id uuid  → profiles, not null
  item_id    uuid  → topic_material_items on delete cascade, not null
  day        date  not null
  seconds    integer not null default 0   -- прибавляется, не перезаписывается
  max_position integer not null default 0 -- докуда дошёл, только вверх
  duration_seconds integer                -- последняя известная длительность
  updated_at timestamptz not null default now()
  primary key (student_id, item_id, day)
```

Дневная разбивка, а не один итог: весит столько же, но отвечает и на
«сколько всего», и на «занимался ли на этой неделе» — а второе в
разговоре с родителем важнее первого.

**Посекундной истории просмотров не заводить.** Это слежка за
подростком, которая отчёту ничего не добавляет.

Права:

* RLS включена; **прямых `insert`/`update` у `authenticated` нет
  вовсе** — пишет только функция ниже;
* `select` ученику — свои строки (`student_id = auth.uid()`);
* `select` персоналу — строки по материалам своих тем
  (`public.auth_is_staff_of_topic(<тема материала>)`; функция есть,
  ручных копий условий не писать — CLAUDE.md).

RPC — единственный вход на запись:

```
video_watch_add(p_item_id uuid, p_seconds integer, p_position integer,
                p_duration integer default null) returns void
security definer
```

Внутри, по порядку:

1. `p_seconds` вне диапазона 1…30 → выходим молча (клиенту верить
   нельзя, одна кривая отправка не должна давать три часа просмотра);
2. материал существует, `kind = 'video'`, `is_visible`;
3. `public.course_student_can_see_topic(<тема материала>)` — иначе
   отказ: считать просмотры чужого курса нечего;
4. `public.auth_is_staff_of_topic(<тема материала>)` — если да,
   **выходим молча**: решение владельца №2, просмотры персонала не
   считаются. Именно молча, а не отказом: преподаватель смотрит своё
   видео законно, просто это не статистика;
5. upsert в `video_watch_daily` на `(auth.uid(), item, current_date)`:
   `seconds = seconds + p_seconds`,
   `max_position = greatest(max_position, p_position)`,
   `duration_seconds = coalesce(p_duration, duration_seconds)`.

`revoke all … from public, anon`, `grant execute … to authenticated` —
как у соседних функций контура.

### 2. Клиент: считать честно

Отдельный модуль (например `src/lib/videoWatch.ts`) с чистой функцией
подсчёта — её и проверяй тестами, а не React.

Правило, на котором такие счётчики врут чаще всего:

* прибавляем **не разницу позиций** и **не время на странице**, а
  минимум из двух: сколько прошло по часам между соседними событиями и
  насколько продвинулась позиция (плюс секунда на дрожание). Прыжок в
  конец ролика тогда не даёт сорок минут, а пауза не даёт ничего;
* позиция ушла назад (перемотка назад) → прибавляем ноль;
* между событиями прошло больше ~30 с (вкладка спала) → прибавляем
  ноль, начинаем отсчёт заново;
* вкладка скрыта (`document.visibilityState`) → не копим.

Накопленное отправляем раз в ~30 секунд и обязательно на паузе, на конце
ролика, при уходе со страницы и при размонтировании — иначе последние
минуты каждого сеанса теряются, а это как раз самые частые сеансы.

### 3. Где это сразу видно

Чтобы правка не легла мёртвым грузом до отчёта:

* **ученику** — отметка «просмотрено» у материала, когда
  `max_position` дошёл до ~90 % длительности. Минуты ему не
  показываем (решение №1);
* **персоналу** — в карточке ученика строка «видео: N минут за неделю,
  M всего, с <дата первой записи>». Найди, где сейчас показывается
  карточка ученика у преподавателя, и встрой туда одну строку; если
  подходящего места нет — скажи в отчёте и не выдумывай новый экран.

## Границы

- Плеер и вёрстку материалов не переделывать: только приёмник событий и
  отправка счётчика.
- YouTube и Vimeo — шов, но не реализация.
- `bunny_video_stats_cache`, edge-функцию `bunny-video-stats` и админский
  экран «Видео» не трогать: это про другое (сводка по видео, а не по
  ученику).
- Отчёт по ученику целиком — не здесь.
- Зависимостей не добавлять: протокол player.js пишется руками, это
  несколько десятков строк.
- Миграцию **не применять**.

## Приёмка

- Тесты (чистая функция подсчёта, без React): обычное воспроизведение
  даёт секунды; пауза — ноль; перемотка вперёд не даёт больше, чем
  прошло по часам; перемотка назад — ноль; разрыв больше 30 с — ноль и
  перезапуск; скрытая вкладка — ноль.
- Тесты приёмника сообщений: чужое сообщение игнорируется; сообщение не
  из того iframe игнорируется; при отсутствии событий не отправляется
  ничего.
- Тесты экрана: отметка «просмотрено» появляется при 90 % и не раньше;
  минут ученику не видно; строка у персонала показывает минуты и дату
  начала записи.
- SQL-пробы под ролями (в откатываемом блоке, `raise exception` в
  конце): ученик курса пишет через RPC и видит свою строку; чужой ученик
  — отказ; персонал видит строки своих учеников; персонал сам пишет —
  строк не появляется; `p_seconds = 600` — строк не появляется.
- Харнесс: тема с видео у ученика (с отметкой и без), карточка ученика у
  преподавателя — 1280 и 390, `../patches/055-shots/`.
- Полный `npx vitest run` — ноль падений.
- `npx tsc -b > tsc.log 2>&1; echo $?` последним; патч от `origin/main`
  в `../patches/055-video-watch.patch`; отчёт.
