## Задача 1. Прогон с живым эталоном

Владелец запускает проверку на **двух** работах (он делает это руками,
функция требует его сессии — ты запустить её не можешь):

| Тема | Сдана | Файлов | Шкала | `attempt_id` |
|---|---|---|---|---|
| Кинематика… **Теория** | 10.09 | 2 | пятибалльная | `3168dd03-e685-4021-8a30-6b94f8656195` |
| Кинематика… **Первая часть** | 11.09 | 4 | стобалльная | `d61b010c-c609-4b9f-b940-6b6f9c0dc691` |

Обе выбраны не наугад: у каждой темы на проде **есть** файл рубрики
`solution` (173 кБ и 911 кБ) — без него тест бессмыслен. Первая — рабочий
лист, где ученик по условию пишет только ответы; именно на таких модель
ставила 0 и 3 балла. Вторая — работа с полными решениями и тяжёлым
эталоном.

Сразу после прогона сверь по базе **три** вещи и назови их в отчёте:

1. `reference_state` стал `used`, а не `failed`;
2. в `topic_material_text_cache` появились строки — и **каким движком**:
   бесплатным `cloudflare-ai` или платным `mistral-ocr`. Это прямые
   деньги владельца, и он должен знать, какой путь работает;
3. `reference_chars` — сколько символов решения реально уехало в промпт
   (потолок `REFERENCE_CHAR_LIMIT = 14 000`, обрезка с хвоста).

Балл, который владелец считает справедливым, спрашиваешь у него сам, в
своём чате, по каждой работе и с указанием шкалы. **Без его оценок
сравнивать не с чем** — модель нельзя чинить по ощущению «плохо
проверяет».

## Задача 2. Две правки промпта, видные уже сейчас

Обе выведены из разборов на проде, а не из общих соображений. Обе — в
`buildPrompt` внутри `check-homework-ai/index.ts`.

**Первая: модель сама придумала правило «нет хода решения — ноль».**
Дословно из разбора на 0 баллов: «Все задания засчитаны как неверные
из-за отсутствия хода решения». Из разбора на 3 балла: «Нет решения,
только ответы». Но в рабочем листе ученик по условию и пишет только
ответ — это не нарушение, это форма задания. В промпте сейчас есть
строка «Балл снижают только неверный результат и неверный ход», и её
оказалось мало. Нужна явная: отсутствие развёрнутого решения само по себе
ошибкой не является, если задание требует ответа; оценивай тогда по
ответам.

**Вторая: без эталона модель всё равно ставит балл — и ставит ноль.**
Когда сверить ответы не с чем, честный выход — не занижать, а сказать об
этом: низкая уверенность и прямая оговорка в разборе. Ноль, выставленный
вслепую, для преподавателя хуже, чем отсутствие балла: он выглядит как
результат проверки.

**Правь точечно.** Промпт переписан не будет: в нём уже лежат решения,
оплаченные прошлыми ошибками, — «сначала реши сам», «прав автор, а не
ты», методика подсчёта доли верных заданий, оговорка про распознавание
формул. Каждую свою строку добавляй рядом с комментарием, из какого
разбора она выросла.

## Задача 3. Почему падал бесплатный движок — мы до сих пор не знаем

В `loadReference` переменная `lastReason` перезаписывается на каждом
движке, и в `last_error` уезжает причина **последнего**. Поэтому пять
раз подряд мы читали про баланс `mistral-ocr` и ни разу — про то, что
случилось с `cloudflare-ai`, который шёл первым и тоже не справился.

Собирать причины по всем движкам и складывать в одну строку. Диагностика,
которая теряет первую половину причины, хуже отсутствия диагностики: она
уводит в сторону.

## Задача 4. Фильтр по теме в очереди проверки

Просьба владельца дословно: «фильтрация идёт только по дням, а надо ещё
по курсу (уже реализована) и там можно ещё темы — только те, которые есть
в сданных работах».

На `HomeworkReviewQueuePage.tsx` уже есть фильтр по курсу
(`data-testid="queue-course-filter"`) и группировка по дням
(`groupByDay`). Добавляется третий — по теме, рядом с курсом:

- список тем строится **только из строк самой очереди**, а не из
  справочника тем. Тема без сданных работ в списке не появляется;
- выбран курс — в списке тем остаются только темы этого курса.
  Иначе владелец выберет тему из другого курса и получит пустой экран;
- `data-testid="queue-topic-filter"`;
- сброс фильтров (он в файле уже есть, строка 635) должен сбрасывать и
  тему;
- смена курса, при которой выбранная тема больше не подходит, сбрасывает
  тему, а не оставляет пустую выдачу;
- пустой результат объясняется словами, а не пустотой: в файле уже
  различаются «очередь пуста» и «фильтр всё отсёк» — держись этого
  различия.

Тест — в существующий `HomeworkReviewQueuePage`-тест, второго файла не
заводить. Скриншоты 1280 и 390 в отчёте.

## Границы

- **Рендер PDF, координаты рамок и CPU-бюджет не трогать.** `MAX_PAGES`,
  `RENDER_BUDGET_MS`, порядок BGRA→RGBA, литеральные специферы импортов —
  всё это подобрано замерами и уже стоило трёх сгоревших работ. Менять
  только по отдельному решению владельца.
- **Модель и порядок движков по умолчанию не менять.** `AI_MODEL`,
  `AI_PARSE_MODEL`, `ENGINE_ORDER` — это деньги владельца; предложение
  можно, самовольная смена — нет.
- Пороги `MIN_MEANINGFUL_TOTAL` / `MIN_MEANINGFUL_PER_PAGE` тоже не
  крути без нужды: они стоят против молча принятого мусора, который лёг
  бы в кэш как эталон.
- Ключи и секреты в чат, в консоль и в отчёт не печатаются. Никаких
  токенов от имени владельца.

## Порядок

Короткий план оркестратору **до кода**: какие строки промпта добавляешь,
как собираешь причины по движкам, как устроен фильтр по теме. Кода до
согласования не пиши.

Правки функции — через MCP `deploy_edge_function`. Если понадобится
миграция (по этой работе не должна) — только MCP `apply_migration` плюс
файл в `supabase/migrations/` с именем, **точно равным** версии в
`schema_migrations`; `supabase db push` — никогда.

Ветка `work/ai-check-quality`, пушишь её сам, в `main` не пушишь. Раздел
PROJECT_STATE — хвост плюс один в момент записи. Проверка типов
**`npx tsc -b > log 2>&1; echo $?`** буквально последним действием
(`npx tsc --noEmit` в этом проекте не проверяет ничего). Тест каждого
меняемого файла.
