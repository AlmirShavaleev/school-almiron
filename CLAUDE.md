# Инструкции для агента (Claude Code)

Читается автоматически при старте. Здесь — только то, что нельзя вывести из
кода и что дорого узнавать методом проб. Актуализировано 13.09.2026
(аудит оркестратора 12.09 + проверка по коду и `main`, board/018).

## Что это

«Школа Almiron» — платформа подготовки к ЕГЭ/ОГЭ.
Vite + React 19 + TypeScript + Tailwind, Supabase (Postgres + PostgREST + RLS +
Storage + Edge Functions), Vitest, Playwright.
Прод: **alminion.ru**, Vercel собирает автоматически из ветки `main`.

## Порядок работы — три файла, читать в этом порядке

| Файл | Зачем |
|---|---|
| `ОРКЕСТРАЦИЯ.md` | Карта: кто чем занят, зоны, состояние на сегодня, действующие правила и уроки. Короткий намеренно. История — в `ОРКЕСТРАЦИЯ_ЖУРНАЛ.md`, читать точечно. |
| `РАБОЧИЙ_ПРОЦЕСС.md` | Ветки, превью, автопроверка, общий каталог, worktree, что делает владелец. |
| Своя вводная (`*.md` в корне, названа в карте) и задачи в `board/` | Что именно делать. |

`PROJECT_STATE.md` — хронология решений по разделам `§N`. Целиком не
читать (1 МБ); читать разделы, названные во вводной как «родня», и хвост.
Свою работу дописывать в конец новым разделом — **номер выдаёт
оркестратор**, пока несданных веток больше одной. Писать причину, а не
только перечень изменений: причина потом стоит дороже диффа.

`MIGRATIONS.md` — порядок работы с миграциями, обязателен перед любым
изменением схемы.

## Миграции — самое важное правило

**Никогда не запускать `supabase db push`.** Миграции применяются только
MCP `apply_migration`. После применения SQL сохраняется в
`supabase/migrations/` файлом, имя которого ТОЧНО совпадает с записью в
`supabase_migrations.schema_migrations` на удалённой базе. Порядок:
**сначала применить, прочитать фактическую версию из
`schema_migrations`, потом назвать файл** — обратный порядок дважды давал
расхождение имени.

База одна на всех веток: миграции только добавляющие; ломающие — через
оркестратора в два шага.

Права проверять **на проде через MCP**, под ролью `authenticated` и под
тем, у кого прав меньше всего (ученик, посторонний преподаватель):

```sql
select set_config('role','authenticated',true),
       set_config('request.jwt.claims','{"sub":"<uuid>","role":"authenticated"}',true);
select public.<функция>(...);
```

Две ловушки (§29.4): `set_config` и проверяемая функция в одном списке
выборки — порядок вычисления не гарантирован, `set_config` выносить в
подзапрос `FROM` или отдельным оператором; проба под владельцем таблиц
RLS не проверяет — он её обходит. Под владельцем платформы (роль admin +
строка `teachers`, §73) половина ошибок прав не воспроизводится вовсе.

## Устройство прав (тут живут почти все баги)

Права на курс проверяются функцией **`course_is_staff(course_id)`**: админ
платформы, владелец курса, преподаватель группы, куратор группы (легаси
`groups.curator_id`) и куратор курса (`course_curators`). **Любую новую
проверку «персонал ли этот человек по курсу» делать через
`course_is_staff`**, не переписывать условия руками — рассинхрон копий
породил §21 и §29.

- `groups.teacher_id` / `groups.curator_id` — ссылки на `teachers.id` /
  `curators.id` (таблицы ролей с `profile_id`), **не** на `profiles.id`.
- `is_admin_or_owner()` — платформенная роль, не «владелец курса»; владелец
  курса — `auth_is_course_owner(course_id)`.
- Один курс = одна группа (`groups_one_per_course`, §61/§64).
- Ученик может быть закреплён за несколькими преподавателями
  (`teacher_students`, уникальность по паре); проверять «есть ли моя
  связь», а не «чья связь первая» (§150.1).
- Политики на `realtime.messages` для `hw-review:<course_id>` тоже через
  `course_is_staff`; асимметрия «писать всем, читать админу» на канале
  **не работает** — без `select` нет и `track()` (§148). Присутствие в
  школе — таблица `school_presence`, закрытая целиком, только
  definer-функции.

**Симптом RLS-бага, похожий на «нет данных»:** `!inner`-джойны ростера
молча выбрасывают строки без прав. Пустой список — повод проверить права.

## ИИ-проверка ДЗ — граница, которую нельзя двигать

`supabase/functions/check-homework-ai`: рабочие модули — `index.ts` и
`reference.ts`. `parse.ts` и `providers.ts` там же — мёртвый код версии
§33 (index.ts их не импортирует с 8db0f89), удаление подготовлено
(§149.1), но на момент этой правки **ещё не влито в `main`** — если
файлы уже пропали, значит слияние состоялось, эту строку убрать.

**ИИ никогда не пишет в `topic_homework_reviews`.** Он готовит черновик;
вердикт ставит человек. Рамки ИИ переносятся в `annotation_sets` только
по нажатию преподавателя.

Эталон для промпта — рубрика `solution` (авторское решение ДЗ) материалов
темы, `task_solution` (разбор задач урока) не используется намеренно.
Разбор PDF — бесплатным движком с кэшем в `topic_material_text_cache`
(§137). Провайдер сменный: `AI_MODEL` (по умолчанию
`qwen/qwen3-vl-235b-a22b-instruct`), `AI_BASE_URL`, `AI_API_KEY`
(запасное имя `OPENROUTER_API_KEY`); смена без передеплоя. Координаты
рамок — доли страницы 0..1. PDF рендерится на сервере: литеральные
спецификаторы динамических импортов, `jpeg-js` (нативных аддонов в Edge
Runtime нет), **2 с CPU на запрос** — отсюда `RENDER_BUDGET_MS` (§48).
Логика `index.ts` тестами vitest не покрыта — единственная проверка
деплой; чистое выносить в модули по образцу `reference.ts`.

## Проверки — точные команды

- Типы: **`npx tsc -b > log 2>&1; echo $?`** (= `npm run typecheck`),
  буквально последним действием. **`npx tsc --noEmit` в этом репозитории
  не проверяет ничего** (корневой `tsconfig.json` — `references`, без `-b`
  список файлов пуст) — на этом была серия красных сборок.
- Тесты: `npx vitest run <файл>` по каждому изменённому файлу; смотреть
  строку `Test Files N passed` — `--reporter=basic` на vitest 4 не
  запускает ничего и выходит с нулём. `… | head` маскирует код выхода.
- Тесты «по тексту исходника» (`expect(src).toContain`) гниют молча — при
  падении сначала `git show HEAD:<файл>`; новые проверки писать
  поведенческими. Зелёный тест обязан ссылаться на живой файл.
- Сгенерированные типы базы отстают от прода — после правки схемы
  перегенерировать MCP, руками не дописывать.
- Учётные записи прода, включая демо-учётки, для скриншотов и живых
  проверок **не использовать** (`board/014`). Харнесс с подменённым
  Supabase пока лежит локально в `screenshots/mobile-audit/harness/`
  (папка `screenshots/` в `.gitignore`, в репозиторий не входит) — его
  перенос в `e2e/harness/` и README к нему поставлены задачей
  `board/016`, на момент этой правки не сделаны. Если `e2e/harness/`
  уже существует — задача сдана, ориентируйся на её README.
