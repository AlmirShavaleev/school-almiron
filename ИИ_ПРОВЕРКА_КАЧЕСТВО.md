## Что такое «качество проверки»

Не «балл совпал с преподавателем» — этого никто не измерял (26 размеченных
работ ФИПИ, `fizika_mr_ege_2026.pdf`, лежат без дела). Качество здесь — это
три вещи, которые преподаватель видит в панели и по которым решает, верить
ли черновику:

1. **Балл следует из разбора.** Если модель признала ошибку в одной задаче из
   шести — балл не может быть максимальным. До v17 балл был свободным числом
   модели; с v17 он считается кодом из таблицы по заданиям.
2. **Находки без выдумок.** Находка «должно быть 0,78, а не 0,78» отнимает у
   преподавателя доверие ко всем остальным — включая настоящие. С v17 такие
   находки отбрасываются кодом, счётчик — `dropped_findings`.
3. **Ошибки, а не похвала.** Преподавателю нужны места, куда смотреть; похвала —
   фон. С v17 `praise` — не больше одной на работу и только при наличии ошибки.

Четвёртое, что качеством управлять пока не умеет никто, — **чтение
рукописных цифр** (§149: «1» как «7», «1» как «9», столбик А/Б, цепочки цифр).
Это глаз модели; лечится только сменой модели, и для этого нужно сравнение
на одних и тех же работах (ниже).

## SQL сравнения версий и моделей

Две последние проверки одной работы рядом — модель, балл, находки по
категориям, токены, отброшенные. Подставить `attempt_id`:

```sql
with j as (
  select j.*,
         row_number() over (partition by j.attempt_id order by j.created_at desc) as rn
    from topic_homework_ai_jobs j
   where j.attempt_id = '<attempt_id>'
     and j.status = 'done'
),
f as (
  select job_id,
         count(*)                                   as findings,
         count(*) filter (where category = 'calc')   as calc,
         count(*) filter (where category = 'logic')  as logic,
         count(*) filter (where category = 'comment') as comment,
         count(*) filter (where category = 'format') as format,
         count(*) filter (where category = 'praise') as praise
    from topic_homework_ai_findings
   group by job_id
)
select j.rn, j.created_at, j.model, j.suggested_score, j.confidence,
       coalesce(f.findings, 0) as findings, f.calc, f.logic, f.comment, f.format, f.praise,
       j.dropped_findings,
       jsonb_array_length(coalesce(j.tasks, '[]'::jsonb)) as tasks,
       (select count(*) from jsonb_array_elements(coalesce(j.tasks, '[]'::jsonb)) t where t->>'verdict' = 'wrong')     as wrong,
       (select count(*) from jsonb_array_elements(coalesce(j.tasks, '[]'::jsonb)) t where t->>'verdict' = 'partial')   as partial,
       (select count(*) from jsonb_array_elements(coalesce(j.tasks, '[]'::jsonb)) t where t->>'verdict' = 'unchecked') as unchecked,
       j.input_tokens, j.output_tokens
  from j left join f on f.job_id = j.id
 where j.rn <= 2
 order by j.rn;
```

Та же картина по всем работам, у которых есть хотя бы две проверки, — для
сравнения модели А и модели Б на одной выборке (после того как владелец
переключил `AI_MODEL` и прогнал те же 14 работ):

```sql
with ranked as (
  select j.*,
         row_number() over (partition by j.attempt_id order by j.created_at desc) as rn
    from topic_homework_ai_jobs j
   where j.status = 'done'
),
f as (
  select job_id, count(*) as findings,
         count(*) filter (where category = 'praise') as praise
    from topic_homework_ai_findings group by job_id
)
select p.full_name as student,
       a.model as model_new,  a.suggested_score as score_new,  a.confidence as conf_new,
       coalesce(fa.findings, 0) as findings_new, coalesce(fa.praise, 0) as praise_new, a.dropped_findings as dropped_new,
       b.model as model_prev, b.suggested_score as score_prev, b.confidence as conf_prev,
       coalesce(fb.findings, 0) as findings_prev, coalesce(fb.praise, 0) as praise_prev, b.dropped_findings as dropped_prev,
       a.input_tokens as in_new, a.output_tokens as out_new,
       b.input_tokens as in_prev, b.output_tokens as out_prev
  from ranked a
  join ranked b on b.attempt_id = a.attempt_id and b.rn = 2
  join topic_homework_attempts t on t.id = a.attempt_id
  join profiles p on p.id = t.student_id
  left join f fa on fa.job_id = a.id
  left join f fb on fb.job_id = b.id
 where a.rn = 1
 order by a.created_at desc;
```

Сводка по моделям — сколько проверок, средний балл, доля praise, отброшенных,
токены (цена считается отсюда):

```sql
select j.model,
       count(*)                                   as checks,
       round(avg(j.suggested_score), 1)           as avg_score,
       count(*) filter (where j.confidence = 'high') as high,
       round(avg(f.findings), 1)                  as avg_findings,
       round(avg(f.praise), 1)                    as avg_praise,
       round(avg(j.dropped_findings), 1)          as avg_dropped,
       round(avg(j.input_tokens))                 as avg_in,
       round(avg(j.output_tokens))                as avg_out
  from topic_homework_ai_jobs j
  left join (
    select job_id, count(*) as findings,
           count(*) filter (where category = 'praise') as praise
      from topic_homework_ai_findings group by job_id
  ) f on f.job_id = j.id
 where j.status = 'done' and j.created_at >= now() - interval '30 days'
 group by j.model
 order by checks desc;
```

## Что менялось в v17 и почему (§180, board/033)

Источник — 30 прогонов v16 12–15.09, из них 15 в выгрузке. Без тетрадей, по
одним текстам модели, видны четыре дефекта; каждый закрыт **кодом**, потому
что правило в промпте модель выполняет не всегда (правило «доля верных» в
промпте было и не работало).

| Дефект в v16 | Что сделано в v17 |
|---|---|
| Балл не следует из разбора: «ошибка в одной из шести» → 5 из 5; две из 16 → 94 | Модель отдаёт таблицу `tasks` (`no`, `verdict`, `student_answer`, `expected_answer`, `note`); балл считает `computeScore`: (correct + 0,5·partial)/(всего − unchecked). Стобалльная — проценты; пятибалльная — 5 от 90 %, 4 от 70 %, 3 от 50 %, иначе 2. `suggested_score` модели в базу не идёт (если таблицы нет — идёт с `confidence = low`, панель его не показывает) |
| Находки-выдумки: «0,78, а не 0,78», «−8 вместо −8», «0,2, а не 0,2» | Два фильтра в `findings.ts`: по таблице (строка `wrong` с равными после нормализации ответами → `correct`, её `calc`/`logic` — долой; `calc` на `partial` с равными — долой, `logic` остаётся: «ответ верный, ход с изъяном» законен по §149) и по тексту (шаблоны «X, а не Y», «X, а у тебя Y», «X вместо Y» с равными X и Y, сравнение по результату после «=»). Счётчик — `dropped_findings`, разбивка — в логах функции |
| Похвала — 39 % находок, потолок 12 съедают praise; похвала под категорией `calc`/`logic` | Лимиты кодом: `praise` ≤ 1 и только при ошибке; `format` ≤ 2; `calc`/`logic`/`comment` — только по строкам `wrong`/`partial` (comment — ещё и `unchecked`), не больше одной на задание; по `correct` — долой. Из промпта убран шаг «отметь удачные ходы» |
| `high` почти везде | `deriveConfidence`: `low`, если `readable=false` или `unchecked ≥ 30 %`; без эталона потолок `medium` (§137); иначе как у модели |

Правила §149 (конфликт с эталоном, «нет хода — не ноль», «без эталона не
занижать») сохранены, переформулированы под вердикты строк. Несверенные
задания перечисляются в summary припиской «Не сверены задания (в балл не
вошли): …».

Чего v17 **не** лечит: чтение рукописных цифр. Если в `student_answer` модель
записала «7», а в тетради «1», таблица будет честно неверной — но теперь это
видно в столбце `tasks` и сверяется за минуту.

## Сравнение моделей — как проводить

1. Владелец переключает `AI_MODEL` в настройках функции (Supabase → Edge
   Functions → secrets), передеплой не нужен.
2. Нажимает «Проверить заново» на тех же 14 работах выгрузки (№1–12, 14, 15).
3. Второй SQL выше даёт таблицу «новая / предыдущая» по каждой работе; третий —
   сводку по моделям и токены для цены.
4. Решает по трём вещам: `dropped_findings` (меньше — модель меньше
   выдумывает), число `unchecked` (меньше — лучше читает), и по 3–4 работам,
   где ответы известны (№12 Степанов, №10 Рахматуллин, №8 Райнур) — совпали
   ли `student_answer` с тетрадью.

Кандидаты — в §180 и в отчёте board/033; цены проверять на
openrouter.ai/models на дату решения, они меняются.
