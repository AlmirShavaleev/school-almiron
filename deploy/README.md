# Выкладка фронтенда Almiron на VPS

GitHub Actions запускает выкладку вручную из `main`. До подключения к VPS workflow проверяет тесты публикации файлов, граф ссылок сборки, миграцию телеметрии и сценарии восстановления в Chromium. Каждый запуск получает ID вида `<commit>-<run>-<attempt>`. Тот же ID записывается в JavaScript, `version.json` и имя каталога релиза.

## Первое включение

1. Сохранить текущую конфигурацию Nginx и зафиксировать цель `readlink -f /srv/almiron/current`. Перед изменениями проверить свободное место и права доступа для `almiron-deploy` и пользователя Nginx. Скрипту нужен Python 3.12+.
2. Если журналы или архивы содержат `useStudentTopicJournal-DTw7_tVx.js`, проверять его в составе исходной сборки вместе с её зависимостями. Публиковать файл под старым именем следует только из подтверждённого артефакта этой сборки.
3. Запустить от пользователя деплоя `python3 scripts/deploy-vps.py seed`. Скрипт переносит assets из всех сохранённых каталогов релизов и добавляет отсутствующие `version.json` для отката. `current` остаётся на активной версии. При конфликте содержимого публикация останавливается и выводит имя файла.
4. Адаптировать `nginx-frontend.locations.conf` к существующему виртуальному хосту. Заменить прежние блоки для тех же путей, сохранив сертификаты, настройки журналов и остальные маршруты. Проверить `nginx -t`, затем штатно перечитать конфигурацию. До первой новой выкладки убедиться на `www`, что активный и старый хешированные JS возвращают JavaScript с `200`, вымышленный JS получает `404`, а `version.json` возвращает версию активного каталога и `Cache-Control: no-store`.
5. Применить совместимую миграцию `perf_asset_failure_diagnostics` перед выкладкой нового фронтенда. Сначала проверить её в изолированной базе. Старые вызовы `perf_ingest` продолжают работать. Новые события ошибок не связываются с профилем ученика.
6. После подтверждения запустить ручной workflow. С VPS по публичному HTTPS проверяются версия, HTML и типы входных JS и CSS. Затем на тестовом аккаунте проверить авторизацию, уроки, отправку работ, загрузку фото и переход к другому уроку из старой вкладки.

## Откат

Публикация удерживает блокировку до завершения публичной проверки. После трёх неудачных проверок скрипт возвращает `current` к предыдущему релизу, если ссылка ещё указывает на проверяемую сборку, и проверяет предыдущую версию по HTTPS. Workflow в этом случае завершается с ошибкой. Если HTTPS-проверка после возврата тоже не проходит, в журнале указываются восстановленная версия и причина ошибки проверки.

`python3 scripts/deploy-vps.py rollback <release-id>` атомарно переключает `current` с той же блокировкой. После ручного возврата проверить `version.json`, входной JS и чанк урока восстановленной версии. Assets обеих сборок остаются доступными.

## Инвентаризация assets

`python3 scripts/deploy-vps.py cleanup-dry-run --min-age-days 30` выводит список файлов вне всех сохранённых релизов и учитывает время последнего изменения. Команда не создаёт файлов, не удаляет assets и останавливается, если не может проверить набор релизов. Перед возможным удалением нужен отдельный контроль старых вкладок и резервных артефактов.

## Диагностика

Сервер допускает до 12 запросов `perf_ingest` одним авторизованным отправителем сразу. Затем восстанавливается один запрос каждые пять секунд. Учёт ведётся в закрытой служебной таблице. Сами диагностические события остаются без профиля. Для гостя RPC закрыт. После проверки сохранности диагностических данных можно отдельно утвердить очистку служебных строк, у которых `next_at` старше суток. На штатную загрузку и отправку работ этот учёт не добавляет запросов.

## Локальные проверки

```sh
node --test scripts/audit-build-assets.test.mjs
node scripts/audit-build-assets.mjs dist
python3 scripts/test-deploy-vps.py
npx playwright install chromium
node --test scripts/test-deploy-browser.mjs
node scripts/measure-frontend.mjs /path/to/baseline/dist dist --load
```

Браузерные тесты используют два локальных билда и синтетические аккаунты. Нагрузочный режим открывает урок в холодных вкладках группами из 1, 5, 10, 20 и 30 учеников. Запросы Supabase в измерении обрабатываются заглушкой Playwright. Для проверки реальной конкуренции запросов к лимитеру используйте `scripts/test-perf-pg17.mjs` на отдельном PostgreSQL 17 в пустой локальной БД `almiron_preflight`, передав путь к клиенту `pg` через `ALMIRON_TEST_PG_CLIENT`.
