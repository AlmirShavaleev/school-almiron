# Каталог задач — вводная для отдельного чата

Этот файл **дополняет** `CLAUDE.md`, а не заменяет его. Там общие правила
проекта (миграции, права, три контура ДЗ, тесты) — их читать первыми. Здесь
только то, что относится к каталогу и чего в общих правилах нет.

Писал агент из соседнего чата, где идёт работа по домашним заданиям. Значит,
над одним репозиторием одновременно работают двое — раздел «Как не подраться за
файлы» в конце обязателен к прочтению.

## Четыре вещи, которые надо знать до первой правки

### 1. Картинки живут на Cloudflare R2, а не в Supabase

Самое важное. В июле проект упал: бакет `catalog-assets` занимал 2197 МБ при
лимите 1 ГБ, и Supabase ограничил сервис целиком — перестали отвечать REST,
Auth и Storage, войти в школу стало нельзя. **В таком состоянии данные нельзя
даже удалить** — файловый менеджер не работает, S3 закрыт, удаление строк из
`storage.objects` блокирует триггер. Выход был только один: оплатить тариф.
Подробности — `PROJECT_STATE.md` §34.

Поэтому: картинки отдаёт `assets.alminion.ru`, адрес строит `getAssetUrl()` в
`useCatalog.ts` через `VITE_ASSETS_BASE_URL`. Ключи в R2 хранятся
**раскодированными** («1 (1).png»), поэтому каждый сегмент пути кодируется
отдельно. Ветка через Supabase Storage в коде осталась запасной — она
включается, когда переменная пуста.

**Ничего нового в бакет `catalog-assets` не загружать.** Любой импорт задач
должен класть картинки на R2.

### 2. Два режима просмотра — отсюда половина сложности

`CatalogViewMode = 'exam' | 'physics-topics'`.

- `exam` — обычный: разделы = номера заданий экзамена.
- `physics-topics` — только для физики ЕГЭ: разделы **виртуальные**, у них
  нет строки в базе, id вида `physics-topics-section-7`, а темы приезжают из
  связей с `source = 'ai_physics_v1'` (константа `AI_PHYSICS_SOURCE`).

Счётчики задач в этом режиме считает не клиент, а RPC
`get_catalog_topic_counts_by_source` / `get_catalog_section_task_counts_by_source`.
Правя фильтрацию, всегда проверяй оба режима: правка «по-очевидному» в одном
почти всегда ломает другой — на этом уже спотыкались.

### 3. `catalog_task_topics.source` — не декоративное поле

Легаси-связи (без `source`) и связи, проставленные разбором физики
(`ai_physics_v1`), живут в одной таблице. `exam`-режим обязан видеть **все**
связи, `physics-topics` — только свои. Два красных теста ниже как раз про это.

### 4. Права простые, но чтение открыто всем вошедшим

На всех таблицах каталога: `*_select_auth` — читать может любой
аутентифицированный, `*_all_admin` — писать только админ/владелец.
`catalog_task_progress` — своё у каждого (`select/insert/update/delete_own`)
плюс чтение админом. Публичного доступа нет: анониму каталог не виден.

## Хвост производительности

`useCatalog.ts` собирается в чанк **1.16 МБ** (238 кБ gzip) — самый тяжёлый в
проекте, вдвое больше входного. Один файл на 1446 строк держит и типы, и
константы предметов, и все запросы обоих режимов. Разделить его — заметная
работа с высоким риском конфликтов, поэтому браться за неё стоит только
осознанно и лучше отдельным заходом, а не попутно.

## Как проверять

```bash
npx tsc --noEmit
npx vitest run src/pages/catalog/__tests__/catalog-qa.test.ts
npx vite build
```

Полный `vitest run` в облачной песочнице упирается в таймаут — гонять точечно.
E2E оттуда не запускается: egress-прокси блокирует `*.supabase.co`.

## Как не подраться за файлы

Над репозиторием одновременно работают два чата. Правило простое: **каталог
трогает только этот чат**, домашние задания и проверка работ — соседний.

Файлы соседнего чата, руками не править:

```
src/components/SubmissionReviewer.tsx
src/lib/annotationGeometry.ts
src/pages/HomeworkReviewQueuePage.tsx
src/components/courseProgram/TopicHomework*.tsx
src/hooks/useTopicHomework*.ts, useHomeworkAiCheck.ts, useQueueAiJobs.ts
supabase/functions/check-homework-ai/
```

Общие файлы, где столкновение вероятнее всего:

- **`PROJECT_STATE.md`** — только дописывать в конец новым разделом. Номер
  сначала смотри в реестре `ОРКЕСТРАЦИЯ.md`, потом сверяй с фактическим хвостом
  файла: §45 занят (твой же раздел), §46 зарезервирован за ИИ-проверкой.
- **`src/AppRoutes.tsx`**, `CLAUDE.md`, `package.json` — сначала посмотреть
  `git status`, не тронуты ли они уже.

И перед началом работы, и перед коммитом: `git pull`. Соседний чат пушит в
`main` несколько раз за сессию.

## Порядок работы, принятый в проекте

1. Миграции — **никогда** `supabase db push`. Только MCP `apply_migration`,
   и следом сохранить тот же SQL файлом в `supabase/migrations/` с именем,
   ТОЧНО совпадающим с записью в `supabase_migrations.schema_migrations`.
2. Пушит и деплоит владелец, не агент. Задача агента — довести сборку до
   зелёной и отдать команды.
3. Свою работу дописать в `PROJECT_STATE.md` новым разделом — с причиной, а не
   перечнем изменений. Причина потом стоит дороже диффа.
