# Кто чем занят

Рабочая карта на время, пока над проектом идут несколько параллельных чатов.
Держит её чат-оркестратор; остальные читают свою вводную и этот файл.

**Этот файл короткий намеренно** (с 12.09): чаты читают его целиком на
старте, и 230 КБ журнала на каждый старт — это десятки тысяч токенов ни
на что. Вся история решений, закрытые вопросы, старые чек-листы и полный
реестр разделов — в `ОРКЕСТРАЦИЯ_ЖУРНАЛ.md`; его читают точечно, по
ссылке, а не целиком.

**Внимание по зоне «Дизайн»:** её вводная выдана, но результата на диске
нет — ни аудита, ни гайда с токенами. Пока их нет, ссылаться на «палитру
дизайн-системы» нельзя: документа с токенами не существует. Токены до
появления гайда задаёт тот чат, который делает работу, — локально и
одним блоком; при появлении гайда переименовываются в одном месте.

**С 26.08 действует `РАБОЧИЙ_ПРОЦЕСС.md`** — читать наравне с этим
файлом и `CLAUDE.md`. Коротко: одна работа = одна ветка `work/*`; чат
коммитит и пушит СВОЮ ветку сам, в `main` пушит только владелец; каждая
ветка получает превью Vercel и автопроверку GitHub (`tsc -b` + оба
набора тестов) — красный CI значит «работа не сдана»; база общая, поэтому
миграции только добавляющие, ломающие — через оркестратора в два шага;
edge-функции общие, деплой ломающей версии ждёт слияния.

Общие файлы, где столкновение вероятнее всего: `PROJECT_STATE.md`,
`CLAUDE.md`, `src/AppRoutes.tsx`, `package.json`.

Общая SQL-функция: `topic_homework_submit_attempt` — сдачу работы ведёт чат по
ИИ-проверке, блок уведомления внутри неё принадлежит чату по Telegram.

**Общее определение «тема пройдена» (решение оркестратора 11.09).**
Отметки в `topic_section_marks` хранятся по рубрикам (`group_key`), и
«тема пройдена» — это не «есть хоть одна отметка», а то, что считает
клиентский `topicDone` (все рубрики, которые у темы реально есть). В
базе это определение живёт **в одной функции**, которую заводит чат
карточек (§152, ветка `work/live-cards` — она сдаётся первой), а чат
учебного плана (§151) **переиспользует**, не заводя свою. Два разных
«пройдено» на вкладке «Сейчас» и в плане — это два числа, которым
владелец перестанет верить. Живая цифра на 11.09: 61 отметка рубрик, 33
пары «ученик, тема» по мягкому определению; строгое даст не больше 33.

## Уроки, которые действуют (короткий список)

  остановиться (просрочка ДЗ, 09.09).

  готовые ответы (лендинг вместо платформы, 26.08).

## Что делает оркестратор, когда чат отчитался

1. Смотрит прод, а не отчёт: состояние в базе, версия функции, деплой Vercel.
2. Проверяет, не залез ли чат в чужую зону (`git status` до и после).
3. Сводит: не конфликтуют ли правки разных чатов в общих файлах.
4. Выдаёт следующий номер раздела и обновляет этот файл.

## Неизменные правила проекта

- Проба под `set role authenticated`, читающая ту же таблицу, что проверяет,
  умеет молча самоустраняться из-за RLS: отсутствие строки в результате — не
  «успех», а повод перечитать от владельца (урок §54).
- `notification_queue` — общая таблица: уборка тестовых строк ТОЛЬКО по
  своему deduplication_key или entity_id, никогда по event_type (урок §71:
  снесён след доставки чужой живой выдачи, риск повторной карточки).
- **`tsc --noEmit` в ЭТОМ репозитории не проверяет НИЧЕГО** (найдено чатом
  контура курса 11.08, подтверждено оркестратором по диску). Корневой
  `tsconfig.json` — это `{"files": [], "references": [app, node]}`; без `-b`
  компилятор честно проверяет пустой список и выходит с нулём. Доказано
  намеренной ошибкой: `const __probe: number = "строка"` → `--noEmit` даёт 0,
  `-b` даёт TS-ошибку и код 2.
  **Правильная команда: `npx tsc -b > log 2>&1; echo $?`** (она же
  `npm run typecheck`), буквально последним действием.
  Историческое: правило про `--noEmit` я требовал во ВСЕХ вводных с §68 —
  это была моя ошибка, а не халатность чатов. Отсюда вся серия красных
  сборок при «зелёном tsc» (§89, §93.6, §100, шесть ошибок пакета
  §101–§110, `CopyDialogs` в §113): единственной настоящей проверкой типов
  был `tsc -b` внутри `npm run build` на Vercel, то есть уже после пуша.
  Обвинения в адрес чатов по этим случаям сняты.
- `… | head` маскирует код выхода — `$?` берётся от head. Никаких конвейеров
  поверх проверки (урок §68.4).
- **`npx vitest run --reporter=basic` на vitest 4 не запускает НИЧЕГО** и
  выходит с кодом 0: репортёр удалён (найдено чатом регистрации в §134, он
  сам на этом напоролся). Смотреть строку `Test Files N passed`, а не только
  `$?`. Родня уроку про `| head`: зелёный код возврата не равен пройденным
  тестам.
- Прогон тестов перед отчётом обязан включать тест ТОГО файла, который
  менялся — смежность «на глаз» пропускает именно его (урок §93.6:
  правка страницы прогнана без теста самой страницы, файл упал целиком
  у соседней зоны).
- Сгенерированные типы базы — НЕ страховка: они отстают от прода, tsc
  проходит с устаревшими сигнатурами RPC (дважды: §59.7 и §75 — ручная
  дописка типов затем уронила сборку). После правки схемы сигнатуры
  проверять по проду, типы перегенерировать MCP, руками не дописывать.

- Миграции — только MCP `apply_migration`, **никогда** `supabase db push`;
  файл в `supabase/migrations/` с именем, ТОЧНО совпадающим с записью в
  `supabase_migrations.schema_migrations`.
- Пушит и деплоит владелец, не агент.
- Файлы кладутся владельцу на диск в `D:\Школа Almiron` — облачная копия
  репозитория не источник правды. После 2026-08-03 жёстче: НИКАКИХ утверждений
  о состоянии кода по облачной копии — только диск владельца или задеплоенное.
  На этом сгорели дважды: «красные тесты каталога» и обе «поломки» в
  ТГ_УВЕДОМЛЕНИЯ.md, которых в актуальном коде уже не было.
- Свою работу дописывать в `PROJECT_STATE.md` с причиной, а не перечнем
  изменений.
