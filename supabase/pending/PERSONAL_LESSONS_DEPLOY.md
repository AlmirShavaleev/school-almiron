# Личные занятия — отдельная ветка work/personal-lessons

## Условия

45 минут, 1500 ₽, математика или физика, один преподаватель — Альмир.
Телемост; перенос учеником не позднее чем за 2 часа, повторная оплата не нужна.
Подписка курса и разбор — независимые продукты. Неподтверждённых правил
штрафов, отмены и возвратов нет: по этим вопросам интерфейс направляет к преподавателю.

## Просмотр

`/preview/tutoring` — автономная демонстрация с вымышленными окнами и локальным
подтверждением без запросов записи и без создания платежей.
`/preview/landing#personal-help` — блок личной помощи в существующем лендинге.
`/tutoring` — настоящий календарь и свои занятия. Гость видит свободные даты,
затем входит или регистрируется как ученик; намерение сохраняется на сутки.
`/admin/tutoring` — ссылка Телемоста, включение записи, добавление окон и записи.
Кнопка из темы передаёт её название в описание запроса.

## Подключение после просмотра ветки

Изменения БД и Edge Functions в общей School не применялись.
1. Через MCP применить `personal_lessons.sql`, сохранить фактическую версию
   миграции в `supabase/migrations/` по MIGRATIONS.md.
2. Деплой `tutoring-payment`: index.ts, verify.ts и `_shared/subscription.ts`.
   verify_jwt=true; используются существующие SUBSCRIPTION_YK_SHOP_ID,
   SUBSCRIPTION_YK_SECRET_KEY, SUBSCRIPTION_APP_URL, SUBSCRIPTION_RETURN_ORIGINS.
   Первая версия требует ключ `test_…` и ответ ЮKassa `test=true`; боевой магазин
   не принимает. Изменение этого ограничения — отдельное решение владельца.
3. Деплой `subscription-webhook` с verify_jwt=false (сохранить текущий режим),
   включив также `../tutoring-payment/verify.ts` и `_shared/subscription.ts`.
   Существующий URL уведомлений остаётся прежним. Добавлена отдельная ветка
   по metadata.origin=tutoring_v1, подписочные платежи идут прежним путём.
4. В админке сохранить настоящую ссылку Телемоста, добавить свободные окна
   и включить запись. По умолчанию запись выключена, вымышленных окон в БД нет.
5. Сквозная проверка тестовым магазином: оплата, возврат на сайт, подтверждение,
   ссылка, перенос, отменённая оплата. Подтверждение сверяется по API, сумме,
   назначению, ID и признаку тестового платежа. Вручную статусы не подделывать.

## Надёжность и границы первой версии

Окно резервируется на 15 минут. Повтор checkout использует ID записи как ключ
идемпотентности. Слоты блокируются на сервере; две записи не могут занять одно
время. Поздний платёж при уже занятом окне отмечается payment_conflict и
выводится администратору для согласования/возврата, чужая запись сохраняется.
Подтверждение — через вебхук либо ручную кнопку проверки, без создания нового
платежа. Уведомления Telegram/SMS и загрузка файлов — следующий этап; сейчас
ученик описывает запрос текстом и может вставить ссылку на задачу.
Автоматические возвраты не реализованы: возврат в ЮKassa требует ручного
согласования, затем корректировки записи администратором. Не включать боевую
оплату до определения политики отмены/возврата и реализации её обработки.

Таблицы закрыты RLS и без прямых грантов anon/authenticated. Публичная RPC
отдаёт только время свободных окон, свои записи — по auth.uid(). Ссылка встречи
появляется только в оплаченной записи. Все функции имеют фиксированный
search_path и явные EXECUTE-гранты; применение статуса — только service_role.
