# Уведомления администратора об успешной оплате

Получатель — подключённая админская учётная запись owner@almiron.ru (Шавалеев Альмир). Выбрана по подтверждённому профилю и активному telegram_connections; демо-админы не включены. Настройка хранится в admin_payment_notification_settings, а не захардкоженным chat_id в исходниках.

- Триггер subscription_log реагирует только на новую запись payment_succeeded после применения подтверждённой оплаты. Историческая рассылка не выполняется.
- Отдельная admin_payment_notifications с UNIQUE(payment_id,recipient_profile_id); повтор webhook не создаёт повторную строку. Прочие школьные очереди не обрабатываются.
- pg_net запускает admin-payment-notify после коммита; cron раз в минуту повторяет готовые к отправке записи. 3 попытки, SKIP LOCKED, зависшие sending возвращаются через 10 минут.
- Edge verify_jwt=false, но требуется CRON_SECRET в X-Cron-Secret (fail closed). В БД секрет берётся из Vault cron_secret, в клиентах его нет.
- Перед отправкой повторно проверяются роль admin/owner и действующее Telegram-подключение. При возврате платежа до доставки запись отменяется.
- Неизвестный режим оплаты проверяется GET-запросом в ЮKassa; если определить его нельзя, сообщение прямо говорит «режим не проверен». Никогда не называть такой платёж реальным. Тестовые сообщения помечены, реальные списания не создаются.
- Формат: имя, курс, сумма, тип, дата оплаты, текущий доступ до; ссылка на /admin/finance. Имя и курс экранируются для Telegram HTML.
- Health (POST {health:true} с секретом) только проверяет getMe/getChat и конфигурацию, сообщения не отправляет.
- Временный сетевой сбой после фактического приёма сообщения Telegram, но до подтверждения доставки в БД, теоретически может дать повтор при retry. Абсолютная exactly-once доставка внешнему API не гарантируется.
