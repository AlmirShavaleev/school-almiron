# Рабочий процесс: ветки, превью, автопроверка

Решение владельца 26.08. Обязательно к чтению **всем чатам** наравне с
`CLAUDE.md` и `ОРКЕСТРАЦИЯ.md`.

## Зачем меняем порядок

Как было: все чаты правят один и тот же рабочий каталог, владелец копит
изменения и раз в несколько дней делает один общий коммит. Отсюда три
беды, каждая случалась не по разу:

- **красная сборка на проде** — ошибка одной работы валит весь пакет;
- **нельзя откатить одну работу** — они перемешаны в одном коммите
  (26.08 откат лендинга обошёлся в потерю всей сделанной работы);
- **владелец — единственная точка исполнения**, всё ждёт его.

Как будет: **одна работа — одна ветка — своё превью — своя проверка.**

## Правила

### 1. Ветка на работу

Имя: `work/<короткая-тема>` — `work/platform-style`, `work/ai-reference`.
Ветка создаётся от свежего `main`:

```
git checkout main && git pull
git checkout -b work/<тема>
```

### 2. Чаты пушат только свои ветки

Решение владельца: **чат может коммитить и пушить в свою ветку `work/*`
сам.** В `main` не пушит никто, кроме владельца. Слияние — тоже владелец,
после того как посмотрел превью.

Коммит-сообщение — одной строкой по-русски, что сделано, с номером
раздела: `§139: токены и примитивы кабинета`.

### 3. Превью вместо «соберите у себя»

Vercel собирает каждую ветку и даёт свою ссылку. Владелец открывает её с
телефона и смотрит живьём — без сборки на своей машине, без скриншотов.

В отчёте оркестратору чат обязан назвать **имя ветки**; ссылку на
превью владелец берёт в Vercel (вкладка Deployments, строка своей
ветки).

### 4. Автопроверка

`.github/workflows/ci.yml` гоняет `tsc -b` и оба набора тестов на каждый
пуш в ветку. **Красная проверка — работа не сдана.** Отчёт со словами
«у меня локально зелено» при красном CI не принимается.

### 5. База — общая, и это главная ловушка

Ветки разводят КОД. База у нас одна на всех: миграция, применённая через
MCP, немедленно действует и для прода, который живёт на `main`.

Отсюда жёсткое правило: **миграции только добавляющие.** Новая таблица,
новая колонка, новая функция — можно. Удалить колонку, переименовать,
сузить тип, поменять поведение существующей RPC — нельзя, пока ветка не
влита: старый код на проде продолжает работать со старой схемой.

Если работа требует ломающего изменения — сначала пишешь оркестратору,
разводим по шагам: сперва добавили новое, влили код, потом отдельной
работой убрали старое.

Порядок применения миграций не меняется: **только MCP `apply_migration`
плюс файл в `supabase/migrations/` с именем, точно равным версии в
`schema_migrations`**; `supabase db push` — никогда.

### 6. Edge-функции

Деплой через MCP `deploy_edge_function` разрешён чатам, но помни: функция
общая, ветки её не разводят. Деплой ломающей версии кладёт прод. Если
новая версия функции требует нового кода интерфейса — деплоишь **после**
слияния ветки, а в отчёте пишешь, что деплой ждёт слияния.

### 7. Общие файлы

`PROJECT_STATE.md`, `ОРКЕСТРАЦИЯ.md`, `CLAUDE.md`, `package.json` правят
все — это главные места конфликтов при слиянии. Правило прежнее: раздел
`§N` берётся хвост+1 **в момент записи**, а не заранее. Если при
слиянии владелец получил конфликт в этих файлах — зовёт оркестратора,
разводит он.

### 8. Рабочая папка одна на всех — переключение ветки объявляется

Ветки разводят код, но **каталог на диске владельца один**, и выкачена в
нём в каждый момент ровно одна ветка. Значит, `git checkout` одного чата
меняет файлы под ногами у другого: 11.09 чат ИИ-проверки отошёл от
`origin/main` ровно в ту минуту, когда я сверял работу живой панели, и
её файлы исчезли из каталога прямо посреди сверки. Обошлось только
потому, что панель была уже закоммичена и запушена.

Отсюда правила:

- **переключать ветку можно только с чистым рабочим деревом** — сначала
  коммит и пуш своей ветки, потом `checkout`;
- переключение **объявляется в отчёте** одной строкой: «стою на такой-то
  ветке»; чат, начинающий работу, первым делом называет ветку, на
  которой он находится;
- незакоммиченные чужие файлы не трогаются и не коммитятся — это уже
  соблюдается;
- пропали файлы, которые точно были, — не «сломался диск», а
  переключение ветки соседом. Смотри `git branch --show-current`, прежде
  чем что-то чинить;
- **уходя от клавиатуры, оставляй дерево чистым** — не «скоро вернусь», а
  коммит и пуш своей ветки. Промежуточный коммит в личную ветку ничего не
  стоит: в `main` он не идёт, сообщение переписывается перед сдачей. В
  тот же день, 11.09, чат живой панели уже стоял заблокированным, потому
  что сосед держал каталог грязным: 9 файлов, 431 строка;
- **`git stash` чужой работы запрещён.** Спрятал один, забыл другой — и
  работа живёт в стеке, про который никто не помнит. Каталог освобождает
  тот, кто его занял, своим коммитом.

Если в каталог упрёмся ещё раз, штатным решением станет `git worktree` —
своя папка на ветку. Сегодня он не заводится осознанно: это второй
`node_modules` на диске, а `C:` у владельца забит.

Файлы вне git (`board/`) и файлы с `merge=union` (`PROJECT_STATE.md`,
`ОРКЕСТРАЦИЯ.md`) переключение переживают — проверено.

## Что делает владелец

1. Смотрит превью ветки, решает: годится или нет.
2. Сливает ветку в `main` (кнопкой в GitHub или `git merge`), пушит.
3. Ждёт зелёного Vercel на `main`.

Отказ от работы теперь дешёвый: ветку просто не сливают, и `main` этого
даже не заметил.

## Чего это НЕ меняет

- Секреты: ключи не присылаются в чат и не печатаются в отчётах.
- Учётные записи владельца чаты не используют.
- Прод-данные не правятся молча: любая ручная операция в базе — через
  оркестратора.
