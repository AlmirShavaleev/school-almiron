## 1. Продуктовая модель (актуальная, MVP)

```
Курс → Модуль («Основной», скрыт в UI) → Тема
                                           ├── материалы: текст / видео / ссылка / файл
                                           ├── одно PDF-ДЗ: попытки → проверка → принято/на доработку
                                           └── тестирование из каталога задач  ← НЕ РЕАЛИЗОВАНО
```

Ключевые решения, выстраданные в ходе рефакторинга (не переигрывать без причины):

- Сущности «урок» в пользовательской логике НЕТ. Материалы и ДЗ висят на теме.
  `lessons` — расписание занятий (scheduled_at, group_id, zoom), лежит нетронутым до
  возврата расписания; в MVP не используется.
- Модули технически обязательны (`topics.module_id` NOT NULL), поэтому скрыты:
  триггер `courses_default_module` создаёт модуль «Основной» каждому курсу.
- У PDF-ДЗ нет баллов, дедлайнов и назначения группам. Только
  принято / возврат с комментарием. Несколько попыток, история не затирается.
- Доступ ученика везде один: `group_students → groups.course_id` (+ мёртвая ветка
  `student_courses` — пуста, оставлена на будущее) + `topics.available_from`.
- Конвенция: автор/учитель/проверяющий → `profiles.id` (= auth.uid()),
  ученик → `students.id`. Легаси-системы её нарушают, новые — нет.

## 9. Продуктовые решения владельца (2026-07-26) — рамка MVP

1. **Курс = одна группа.** Новая группа людей = новый курс. Схему не менять,
   это конвенция; UI выбора групп можно упрощать.
2. **Материалы**: пополняются в темах в течение года (текущая реализация ок).
3. **ДЗ существует ТОЛЬКО в теме** (topic_homework). Других систем ДЗ в продукте нет
   и не будет — легаси сносить по карте §4 после обкатки.
4. **Тестирование тем (следующая большая фича, §3)**: задания берутся ТОЛЬКО из
   каталога; проверка ТОЛЬКО автоматическая по ответу, независимо от части (1/2)
   и экзамена (ОГЭ/ЕГЭ). Ручной проверки тестов НЕТ. Следствия:
   - в конструктор теста допускаются только задачи с текстовым эталоном
     (has_answer и непустой ответ после strip тегов; ~16.5 тыс. из 21.8 тыс.);
   - баллы из каталога (max_points), частичные — score_auto_answer/partial_type;
   - снапшот условия/ответа/типа/балла при добавлении в тест — обязателен (см. §3);
   - часть 2 оценивается по ответу «всё или ничего» — осознанное упрощение владельца.

калитку в prevent_role_self_escalation (флаг app.course_join_curator,
только внутри course_join_accept). Ученический аккаунт с членствами
куратором стать не может. Результаты тестов теперь видит персонал курса
привязки (topic_test_assignment_can_view), а не только автор теста.
UI: две карточки ссылок на вкладке «Ученики», список кураторов с
«Убрать» (владелец/админ), curator добавлен в /course-program и
/homework-queue.

## 14. Сессия 2026-07-27 (вечер): курс как рабочее место преподавателя

Сквозная идея этапа: всё, что преподаватель делает с курсом, живёт на одной
странице `/course-program` — программа, материалы, ДЗ, результаты тестов,
ученики и кураторы. Раздел «Группы» скрыт (курс = группа, §9.1), персональные
приглашения из UI убраны.

Короткие сводки по приглашениям и кураторам есть в хвосте §13 — здесь
подробная версия, она приоритетна.

### 14.1. Вкладка «Результаты тестов» — матрица ученики × тесты

`CourseTestResultsSection` (вкладка `testresults` на странице курса).
Раньше результаты теста были видны только внутри банка (`/tests/:testId`,
вкладка «Результаты») — то есть по одному тесту за раз. Здесь обратный
разрез: весь курс сразу.

- Строки — ученики курса (`group_students → groups.course_id`, имена через
  `students → profiles.full_name`, сортировка `localeCompare('ru')`).
  Колонки — привязки тестов к темам курса (`topic_test_assignments` +
  `topic_tests(title)`), сгруппированные по модулям и темам.
- Ячейка = попытка по привязке (`topic_test_attempts`, одна на привязку,
  §10.2): «не начат» / «в процессе» / баллы + процент + дата завершения.
  Цвет процента: ≥70 зелёный, ≥40 янтарный, ниже красный.
- Дата с годом < 2000 показывается как «—»: в базе есть кривые ручные вводы
  (см. §13, `due_at 0002-09-29`), и матрица не должна на них спотыкаться.
- Данные видит персонал курса привязки, а не только автор теста —
  это обеспечивает `topic_test_assignment_can_view` из миграции
  `20260727203959` (§14.2), фронт прав не дублирует.

Ограничение: пустая матрица (нет привязанных тестов) показывает подсказку и
ведёт на программу курса, отдельного UI создания теста здесь нет — он в банке.

### 14.2. Приглашения: две постоянные ссылки — ученики и кураторы

Миграции `20260727202258_course_join_links` и `20260727203959_course_curator_links`
(обе применены через MCP, файлы в `supabase/migrations/`).

Продуктовое решение: персональных приглашений больше нет. У курса есть
**постоянная ссылка** `/join/{token}` и **короткий код** — 6 символов из
алфавита `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (без 0/O/1/I, чтобы диктовать
голосом). И то и другое — своё для каждой роли.

- `course_join_links`: `unique (course_id, link_role)`, `link_role in
  ('student','curator')`. То есть на курс ровно две ссылки, не больше.
  Читать может только персонал курса (`course_join_links_staff_select`).
- RPC (все security definer, роль — необязательный параметр,
  по умолчанию `'student'`): `course_join_link_get(course_id, role)` —
  создаёт ссылку при первом обращении; `course_join_link_rotate` —
  перевыпуск, старые токен и код гаснут; `course_join_link_set_active` —
  «Закрыть/открыть набор»; `course_join_info(value)` — что за курс по
  токену или коду (для страницы `/join` до логина);
  `course_join_accept(value)` — вступление, идемпотентно, группа курса
  создаётся при первом вступлении.
- **Кураторы.** `course_curators` (m2m курс × профиль, `unique(course_id,
  profile_id)`, количество не ограничено). Куратор добавлен пунктом в
  `course_is_staff`, поэтому проверка ДЗ, результаты тестов и программа
  курса открываются ему автоматически — отдельных политик не писалось.
  Убрать куратора может владелец курса или админ
  (`course_curators_owner_delete`), куратор коллег убрать не может.
- **Повышение роли.** Новичок, пришедший по кураторской ссылке,
  повышается `student → curator` через узкую калитку в
  `prevent_role_self_escalation`: триггер пропускает смену роли только при
  выставленном флаге `app.course_join_curator`, а флаг ставится
  исключительно внутри `course_join_accept`. Аккаунт, у которого уже есть
  ученические членства, куратором стать не может — это отсекается там же.
- `/join` принимает и старые персональные приглашения (fallback в
  `studentInvitationAcceptance.ts`), но UI для них убран.

UI: две карточки ссылок на вкладке «Ученики» курса (копировать ссылку / код /
готовый текст приглашения, «Закрыть набор», «Перевыпустить») и список
кураторов с кнопкой «Убрать».

### 14.3. Управление участниками курса

Миграция `20260727163906_course_member_management`, две RPC (security definer):

- `course_member_rename(student_id, full_name)` — переименование ученика
  своего курса. Имя 1–200 символов; право — ученик состоит в группе курса,
  где вызывающий персонал; страховка `profiles.role = 'student'`, чтобы
  через эту калитку нельзя было переименовать преподавателя или админа.
- `course_member_remove(course_id, student_id)` — отчисление: удаляет ученика
  из всех групп ЭТОГО курса. **Аккаунт, попытки и работы не удаляются** —
  журнал и проверенные ДЗ остаются целыми, ученика можно вернуть по ссылке.
  Если удалять было нечего — ошибка «Ученик не найден на этом курсе».

Обе доступны персоналу курса, включая кураторов (через `course_is_staff`).
Вкладка «Ученики» показывает группу, контакты и колонку Telegram (колонка
скрывается, если ни у кого нет привязки или запрос отбило RLS).

### 14.4. Автообновление вкладок и состояние страницы в адресе

Две вещи, которые мешали в обкатке:

1. **Вкладки не обновлялись** после работы в модалке темы: загрузил материалы
   или создал ДЗ — закрыл модалку — матрица и вкладка ДЗ показывают старое,
   помогала только перезагрузка. Введён `refreshKey`: счётчик в
   `CourseProgramPage`, растёт на `onClose` модалки и проброшен пропом в
   `MaterialsMatrix`, `CourseTopicHomeworkSection`, `CourseTestResultsSection`
   (у каждой добавлен в зависимости эффекта загрузки). Проп необязательный
   (`refreshKey = 0`), поэтому компоненты остаются переиспользуемыми.
2. **F5 выкидывал в список курсов.** Выбранный курс и вкладка переехали в
   адрес: `?courseId=…&tab=…`. Гидратация ровно один раз, после загрузки
   списка курсов (иначе нельзя проверить, что курс вообще доступен
   пользователю); неизвестная вкладка и `tab=settings` без прав откатываются
   на `program`. Обратная запись — `setSearchParams(..., { replace: true })`,
   чтобы переключение вкладок не забивало историю браузера. Значения
   `tab` (`program|materials|homework|testresults|students|settings`)
   теперь часть публичного контракта URL — переименовывать нельзя.

Прежний одноразовый deep-link `?courseId=` (им пользовался мастер создания
курса) поглощён этим же механизмом.

### 14.5. Редактор ДЗ упрощён

`TopicHomeworkEditor` (плитка «ДЗ» в модалке темы) переписан. Схема БД не
менялась — только интерфейс и хук `useTopicHomework`.

- **Убраны «Название» и «Инструкция»** вместе с кнопкой «Сохранить».
  У темы одно ДЗ, заголовок «Домашнее задание» ничего не сообщал, а
  инструкция и так живёт в самом файле. Колонка `topic_homework.title`
  осталась NOT NULL — дефолт подставляет хук.
- **Ленивое создание** (`ensureHomework`): строка в базе заводится при
  первом осмысленном действии — загрузке файла или настройке дедлайна.
  Пустых черновиков от случайного открытия плитки больше не появляется.
  Идемпотентна; гонку двух вкладок ловит по `23505` на `UNIQUE(topic_id)`
  и перечитывает существующую строку.
- **Мультизагрузка PDF и картинок с прогрессом** (`uploadHomeworkFiles`):
  signed upload URL + XHR — тот же приём, что в материалах темы (§10.3),
  потому что у supabase-js нет колбэка прогресса. Загрузка
  последовательная (честный прогресс по файлам), есть фолбэк на обычный
  `upload` без прогресса. Если строка в `topic_homework_files` не
  создалась — объект из бакета удаляется, сирот не остаётся.
  Файлы НЕ заменяют друг друга: у ДЗ теперь может быть несколько вложений
  (прежний `uploadHomeworkFile` с `replace = true` оставлен, но из UI не
  вызывается).
- **Список файлов с удалением** (`removeHomeworkFile`): сначала строка (её
  держит RLS), потом объект в бакете.
- **Скриншот из буфера обмена** (Ctrl+V прямо в раскрытой плитке ДЗ).
  Слушатель `paste` висит на `document`, а не на контейнере: у блока нет
  фокусируемого элемента, и требовать «сначала кликни сюда» — лишний шаг.
  Плитка ДЗ рендерится только когда раскрыта (`TopicMaterialsModal`),
  поэтому перехват не залипает на всю страницу; вставка в поля ввода
  пропускается. Имя вставленной картинке даёт чистая
  `nameForPastedImage(fileName, mimeType, index, now)` в
  `src/lib/topicHomework.ts` (+6 тестов): безымянные, `image.png` и
  «Снимок экрана…» превращаются в `screenshot-ГГГГ-ММ-ДД-ЧЧММСС.ext`,
  осмысленное имя из проводника не трогается. Иначе в списке файлов
  выходила стопка неразличимых `image.png`.
- **Дедлайн и шкала баллов** сохраняются сразу при изменении; у поля даты
  выставлен `min` — прямое лечение бага `due_at 0002-09-29` из §13.
- **«Опубликовать» неактивна, пока нет ни одного файла** — публиковать
  пустое ДЗ бессмысленно.
- **Telegram-оповещение — следствие публикации, а не кнопка.** Отдельная
  кнопка «Оповестить» убрана (решение владельца при обкатке 2026-07-27):
  преподаватель про неё забывал, а смысла публиковать молча нет. Нажал
  «Опубликовать» → сразу уходит `topic_homework_notify_students`.
  Дедупликация по ключу `topic_homework:{hw}:{profile}` живёт в RPC,
  поэтому «скрыть → опубликовать» повторно не спамит. Сбой оповещения
  НЕ откатывает публикацию: задание уже видно ученикам, это важнее
  доставки уведомления — о сбое просто пишем плашкой.
  До публикации показывается подсказка «При публикации оповестим в
  Telegram: N», после — «Опубликовано. Оповещено в Telegram: N».
  N считается на клиенте (`topics → modules.course_id → group_students →
  telegram_connections`) и только подсказка; реальный отбор получателей
  делает RPC. Если RLS не отдала `telegram_connections` — подсказки нет,
  публикация работает.
- **Проверки работ в редакторе НЕТ.** Блок `TopicHomeworkReview` из
  модалки темы убран (решение владельца там же): проверка живёт только
  на `/homework-queue` — одна точка вместо двух, ровно как уже сделано
  у ученика со сдачей (§12.3). Модалка темы теперь про ВЫДАЧУ задания.
  Файл `TopicHomeworkReview.tsx` остаётся: из него очередь импортирует
  `ReviewActions`. Сам компонент `TopicHomeworkReview` больше нигде не
  используется (только собственный тест) — кандидат на удаление вместе
  с переносом `ReviewActions` в отдельный файл.
