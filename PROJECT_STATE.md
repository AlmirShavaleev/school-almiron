## 1. Продуктовая модель (актуальная, MVP)

```
Курс → Модуль («Основной», скрыт в UI) → Тема
                                           ├── материалы: текст / видео / ссылка / файл
                                           ├── одно PDF-ДЗ: попытки → проверка → принято/на доработку
                                           └── тестирование из каталога задач  ← НЕ РЕАЛИЗОВАНО
```

Ключевые решения, выстраданные в ходе рефакторинга (не переигрывать без причины):

- Сущности «урок» в пользовательской логике НЕТ. Материалы и ДЗ висят на теме.
  `lessons` — расписание занятий (scheduled_at, group_id, zoom), лежит нетронутым до
  возврата расписания; в MVP не используется.
- Модули технически обязательны (`topics.module_id` NOT NULL), поэтому скрыты:
  триггер `courses_default_module` создаёт модуль «Основной» каждому курсу.
- У PDF-ДЗ нет баллов, дедлайнов и назначения группам. Только
  принято / возврат с комментарием. Несколько попыток, история не затирается.
- Доступ ученика везде один: `group_students → groups.course_id` (+ мёртвая ветка
  `student_courses` — пуста, оставлена на будущее) + `topics.available_from`.
- Конвенция: автор/учитель/проверяющий → `profiles.id` (= auth.uid()),
  ученик → `students.id`. Легаси-системы её нарушают, новые — нет.

## 9. Продуктовые решения владельца (2026-07-26) — рамка MVP

1. **Курс = одна группа.** Новая группа людей = новый курс. Схему не менять,
   это конвенция; UI выбора групп можно упрощать.
2. **Материалы**: пополняются в темах в течение года (текущая реализация ок).
3. **ДЗ существует ТОЛЬКО в теме** (topic_homework). Других систем ДЗ в продукте нет
   и не будет — легаси сносить по карте §4 после обкатки.
4. **Тестирование тем (следующая большая фича, §3)**: задания берутся ТОЛЬКО из
   каталога; проверка ТОЛЬКО автоматическая по ответу, независимо от части (1/2)
   и экзамена (ОГЭ/ЕГЭ). Ручной проверки тестов НЕТ. Следствия:
   - в конструктор теста допускаются только задачи с текстовым эталоном
     (has_answer и непустой ответ после strip тегов; ~16.5 тыс. из 21.8 тыс.);
   - баллы из каталога (max_points), частичные — score_auto_answer/partial_type;
   - снапшот условия/ответа/типа/балла при добавлении в тест — обязателен (см. §3);
   - часть 2 оценивается по ответу «всё или ничего» — осознанное упрощение владельца.

### 14.2. Приглашения: две постоянные ссылки — ученики и кураторы

Миграции `20260727202258_course_join_links` и `20260727203959_course_curator_links`
(обе применены через MCP, файлы в `supabase/migrations/`).

Продуктовое решение: персональных приглашений больше нет. У курса есть
**постоянная ссылка** `/join/{token}` и **короткий код** — 6 символов из
алфавита `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (без 0/O/1/I, чтобы диктовать
голосом). И то и другое — своё для каждой роли.

- `course_join_links`: `unique (course_id, link_role)`, `link_role in
  ('student','curator')`. То есть на курс ровно две ссылки, не больше.
  Читать может только персонал курса (`course_join_links_staff_select`).
- RPC (все security definer, роль — необязательный параметр,
  по умолчанию `'student'`): `course_join_link_get(course_id, role)` —
  создаёт ссылку при первом обращении; `course_join_link_rotate` —
  перевыпуск, старые токен и код гаснут; `course_join_link_set_active` —
  «Закрыть/открыть набор»; `course_join_info(value)` — что за курс по
  токену или коду (для страницы `/join` до логина);
  `course_join_accept(value)` — вступление, идемпотентно, группа курса
  создаётся при первом вступлении.
- **Кураторы.** `course_curators` (m2m курс × профиль, `unique(course_id,
  profile_id)`, количество не ограничено). Куратор добавлен пунктом в
  `course_is_staff`, поэтому проверка ДЗ, результаты тестов и программа
  курса открываются ему автоматически — отдельных политик не писалось.
  Убрать куратора может владелец курса или админ
  (`course_curators_owner_delete`), куратор коллег убрать не может.
- **Повышение роли.** Новичок, пришедший по кураторской ссылке,
  повышается `student → curator` через узкую калитку в
  `prevent_role_self_escalation`: триггер пропускает смену роли только при
  выставленном флаге `app.course_join_curator`, а флаг ставится
  исключительно внутри `course_join_accept`. Аккаунт, у которого уже есть
  ученические членства, куратором стать не может — это отсекается там же.
- `/join` принимает и старые персональные приглашения (fallback в
  `studentInvitationAcceptance.ts`), но UI для них убран.

UI: две карточки ссылок на вкладке «Ученики» курса (копировать ссылку / код /
готовый текст приглашения, «Закрыть набор», «Перевыпустить») и список
кураторов с кнопкой «Убрать».

### 14.3. Управление участниками курса

Миграция `20260727163906_course_member_management`, две RPC (security definer):

- `course_member_rename(student_id, full_name)` — переименование ученика
  своего курса. Имя 1–200 символов; право — ученик состоит в группе курса,

## 16. Сессия 2026-07-28 (2): Telegram-уведомления цикла ДЗ

Продуктовые решения владельца: о сдаче узнаёт ВЕСЬ персонал курса (владелец,
преподаватели групп, кураторы — круг course_is_staff); ученику в сообщение
о проверке кладём вердикт + балл + комментарий (до 300 символов) + ссылку.

Миграция `20260728131304_topic_hw_telegram_events` (применена через MCP,
прогнана на локальном Postgres с заглушками — 6 поведенческих тестов ролями):

- `topic_homework_enqueue_submitted(attempt)` / `topic_homework_enqueue_reviewed(review)`
  — SECURITY DEFINER помощники, ставящие события в notification_queue.
  Сами RPC сдачи/вердикта остаются SECURITY INVOKER (их права держит RLS —
  definer дал бы сдавать чужие попытки), а в очередь ученику RLS писать не
  даёт — отсюда разделение. Помощники проверяют право звонящего на РОВНО ЭТО
  событие (автор попытки / автор review) — спамить чужими событиями нельзя.
- Врезаны в `topic_homework_submit_attempt` и `topic_homework_review_attempt`
  как best effort: сбой очереди даёт WARNING, но НЕ откатывает сдачу/вердикт.
- Событие `topic_homework_submitted` → персоналу: ученик, курс, тема,
  № попытки (если >1), ссылка «Проверить работу →» на /homework-queue.
  Дедуп `topic_hw_submitted:{attempt}:{profile}`.
- Событие `topic_homework_reviewed` → ученику: Принято/На доработку, оценка
  «N из M» (по шкале), комментарий, ссылка «Открыть тему →» на
  /my-course/{group}/topic/{topic}. Дедуп `topic_hw_reviewed:{review}`.
- `topic_homework_notify_students` («новое ДЗ», уходит при публикации):
  в payload добавлена ссылка на тему — раньше сообщение было без ссылки.

Воркер `process-notification-queue` v12 (задеплоен через MCP, репозиторные
копии обновлены): два новых формата сообщений; `new_homework` рендерит
`p.link` (легаси entity_id — фолбэк); в `_shared/variant-telegram.ts`
`topic_homework_reviewed` уважает настройку «проверено» (prefs.checked),
`topic_homework_submitted` идёт по умолчанию.

**Как тестировать с ОДНИМ Telegram-аккаунтом.** В telegram_connections
UNIQUE(telegram_chat_id) — один чат нельзя привязать к двум профилям сразу.
Варианты: (а) содержимое очереди проверяется вовсе без Telegram — сдал/
проверил на сайте и смотри строки в notification_queue (event_type, payload,
status) SQL-ом; доставка как механизм уже доказана обкаткой; (б) для живой
доставки — привязка переключается между профилями: отключить бота в
настройках одного аккаунта, подключить в другом (или админом перекинуть
profile_id у строки telegram_connections). Сначала чат на препода → ученик
сдаёт → приходит «сдал»; потом чат на ученика → публикация и вердикт →
приходят «новое ДЗ» и «проверено». pg_cron дёргает воркер раз в 5 минут.

## 21. КРИТИЧЕСКИЙ баг: ученик по ссылке-приглашению не виден у владельца курса (2026-07-28)

Владелец сообщил (со скриншотом страницы ученика — «Тестовый курс»,
«ПРЕПОДАВАТЕЛЬ: Не назначен», «КУРАТОР: Не назначен», хлебная крошка
«Физика · ЕГЭ · Группа курса»): «странно ученик добавился на курс по ссылке
приглашению, но не отобразился в списке учеников у учителя. и прочерки стоят
в разделе учитель.» + следом «+оотправил ДЗ с аккаунта ученика, оно не дошло
до учителя...».

**Причина.** `course_join_accept(text)` при самом первом вступлении в курс
без единой группы лениво создаёт группу «Группа курса», но НЕ проставляет ей
`teacher_id`/`curator_id` — ссылка ученика на эти поля взяться неоткуда.
Дальше роструется асимметрия двух похожих проверок:

- `course_is_staff(course_id)` (используется в RPC и на уровне курса) уже
  умеет fallback на владельца курса — `exists (select 1 from courses c where
  c.id = p_course_id and c.owner_id = auth.uid())`.
- А вот `auth_is_staff_of_student(stu_id)` и `auth_is_staff_of_profile(pid)`
  (используются НАПРЯМУЮ в RLS SELECT-политиках таблиц `students`/`profiles`)
  такого fallback не имели — только `teacher_id`/`curator_id` конкретной
  группы. `is_admin_or_owner()` тут не спасает — это чисто платформенная
  роль (`admin`/`owner`), а не «владелец этого курса»; у владельца курса
  роль в `profiles.role` обычно `'teacher'`.

Итог: `group_students.select('...', 'groups!inner(...)', 'students!inner(...)')`,
на котором построены и «Ученики», и аккордеоны «Домашние задания» и
«Результаты тестов», использует `!inner`-джойн — RLS тихо режет строку,
которую вызывающий не видит, и ученик просто пропадает из ростера
ВЕЗДЕ разом. Само ДЗ отправлялось нормально (`topic_homework_can_manage` →
`course_is_staff` — fallback на владельца там уже был, запись реально
дошла и видна в БД), просто владелец не мог её найти в том же
сломанном ростере курса.

**Фикс (миграция `20260728210341_fix_student_roster_visibility_for_course_owner`):**
- `auth_is_staff_of_student`/`auth_is_staff_of_profile` — добавлен
  `or public.auth_is_course_owner(g.course_id)`, чисто расширяющее `OR`,
  без сужений.
- `course_join_accept` — ленивая вставка группы теперь ставит
  `teacher_id = (select t.id from courses c left join teachers t on
  t.profile_id = c.owner_id where c.id = v_link.course_id)` — учитель
  по умолчанию = владелец курса, если у него есть строка в `teachers`.
  Остальное тело функции — 1:1 с боевым (там уже есть кураторская ветка
  по `link_role`, `joined_as` в ответе — из миграции `20260727203959`,
  которую я в первый заход по памяти не перепроверил, отсюда и провал
  первой попытки применения, см. ниже).
- Проверено на локальном Postgres 16: владелец теперь видит и `students`,
  и `profiles` строку нового ученика; посторонний учитель — по-прежнему
  нет; ранее назначенный учитель своего ученика видит как и раньше (нет
  regression); auto-created группа получает верный `teacher_id`;
  `course_join_accept` идемпотентна (повторный вызов не плодит группы).
  Есть существующая проверенная триггер-функция
  `_assign_teacher_on_group_insert` (BEFORE INSERT на `groups`,
  миграция `20260719171205`) — она автоматически проставляет
  `teacher_id` только когда группу создаёт САМ учитель (`auth.uid()` с
  ролью teacher); в `course_join_accept` вызывающий — ученик, так что
  этот триггер тут не срабатывает и никак не конфликтует с явным
  `teacher_id` в INSERT (сработает первая же проверка `IF NEW.teacher_id
  IS NOT NULL THEN RETURN NEW`).
- **Провал первой попытки apply_migration**: я исходно собрал фикс по
  памяти на основе `20260727202258_course_join_links.sql`, где
  `course_join_accept` возвращал 3 колонки. К моменту фикса функция уже
  была расширена до 4 колонок (`+ joined_as`) миграцией
  `20260727203959_course_curator_links.sql` — Postgres не даёт молча
  сменить возвращаемый тип через `create or replace function`
  (`42P13: cannot change return type`). Перепроверил боевую сигнатуру
  через `pg_get_functiondef`, пересобрал фикс на РЕАЛЬНОМ текущем теле
  (с кураторской веткой), заново прогнал ту же локальную валидацию —
  вторая попытка `apply_migration` прошла чисто, DROP FUNCTION не
  понадобился.

**Точечный ремонт данных (миграция `20260728210510_repair_orphan_join_group_teacher_id`).**
RLS-фикс закрывает дыру для ЛЮБЫХ групп сразу (не зависит от данных), но
`teacher_id = null` у уже существующей группы означает, что на странице
ученика «Преподаватель» по-прежнему будет «Не назначен», пока данные не
поправлены. Нашёл на проде 6 групп с `teacher_id is null and curator_id is
null`; у пяти из них 0 участников (это либо E2E-тестовые курсы
`[E2E] Цикл ДЗ ...`, либо пустые ручные группы «Софья»/«10 А Лицей
Альметьевск» под курсом «10А» — трогать не стал, скрывать там некого).
Единственная с реальным участником (`member_count = 1`, ученик вступил
2026-07-28 20:33 UTC — это и есть тот самый инцидент) —
группа `b0de3558-0d4d-42f5-a9ea-4b56ad6acec1` («Группа курса», курс
«Тестовый курс», владелец «Учитель 1»/`demoteacher1@demo.local`) —
её `teacher_id` точечно проставлен на `teachers.id` владельца, с теми же
guard-условиями (`GET DIAGNOSTICS`, exception при неожиданном числе
затронутых строк), что и прошлый точечный ремонт в миграции
`20260719171205_assign_teacher_on_group_insert_trigger_and_repair.sql`.

**Не проверено в самом интерфейсе живым кликом** — фикс подтверждён на
уровне RLS/функций (локальный Postgres + прямое чтение боевых
`pg_get_functiondef`), но я не кликал по вкладке «Ученики» реальным
браузером под реальным логином владельца после фикса. Стоит зайти под
своим аккаунтом и проверить, что тот ученик («qweasd»,
`socad46621@kierko.com`) теперь виден в списке и что на его странице
«Преподаватель» больше не «Не назначен».

**Известный, сознательно отложенный хвост**: в `course_join_accept`
ленивое создание группы не защищено от гонки — если два первых ученика
курса вступят одновременно, оба могут создать по отдельной orphan-группе
(`groups.course_id` без уникального ограничения). Не чинил сейчас, чтобы
держать экстренную миграцию минимальной и сфокусированной; тот же паттерн
guard'а, что в `20260728125949_fix_course_join_link_get_race.sql`
(перечитать после `unique_violation`), сюда не переносится напрямую —
там уникальность по `(course_id, link_role)`, здесь её попросту нет.
Если понадобится — отдельная небольшая миграция (либо добавить
уникальный индекс, либо `select ... for update` на курс перед проверкой
«есть ли уже группа»).

### 22.2. База: вторая цель у annotation_sets

Миграция `20260730095422_annotation_sets_topic_homework_attempts`:

- `attempt_id uuid references topic_homework_attempts(id) on delete cascade`,
  `submission_id` теряет NOT NULL, и `CHECK num_nonnulls(submission_id,
  attempt_id) = 1` — ровно одна цель.
- `create unique index annotation_sets_attempt_file_page_key on
  annotation_sets(attempt_id, file_path, page)` — **плоский, не partial**.
  Это важно: PostgREST-овский `upsert` c `onConflict` не умеет использовать
  partial-индекс как арбитра `ON CONFLICT` (для этого сам запрос должен нести
  `WHERE`, повторяющий предикат индекса, а PostgREST его не добавляет).
  NULL-ы в уникальном индексе по умолчанию различны, поэтому legacy-строки
  (`attempt_id is null`) друг другу не мешают, а их уникальность держит
  прежний `unique (submission_id, file_path, page)`.
- Все четыре RLS-политики получили ветку нового контура через уже
  существовавшие хелперы `topic_homework_attempt_can_review` (персонал курса —
  тем же правом, что закрыты сами попытки и файлы) и
  `topic_homework_attempt_is_own` (ученик — только своё и только
  `status='published'`). Ветки старого контура сохранены дословно, добавлен
  лишь явный `submission_id is not null`, чтобы подзапрос не выполнялся для
  строк нового контура.

Проверено на локальном Postgres 16 (`set role authenticated` +
`request.jwt.claim.sub`), 11 проб — все прошли: CHECK ловит обе-NULL и
обе-заполненные; повторный upsert ОБНОВЛЯЕТ строку (1 строка, категория
сменилась), а не плодит дубли; чужой преподаватель не видит (0) и получает
отказ RLS на запись; ученик не видит черновик (0), видит опубликованное (1);
чужой ученик не видит и опубликованное (0); удаление попытки каскадом уносит
рамки. Плюс сухой прогон на РЕАЛЬНЫХ данных прода на попытке того самого
ученика из §21: владелец курса — `can_review = true`, посторонний
преподаватель — `false`, сам ученик — `own = true, can_review = false`.

### 22.3. Аннотатор обобщён на два контура

`SubmissionReviewer.tsx` больше не знает про «сдачу» — он знает про цель:

- Props стали `BaseProps & AnnotationTarget`, где `AnnotationTarget` —
  размеченное объединение `{submissionId} | {attemptId}` с `?: never` на
  противоположном поле. То есть взаимоисключимость целей проверяется на
  этапе компиляции, тем же правилом, что CHECK в базе.
- Внутри — `targetColumn`/`targetId`, и через них все три обращения к
  `annotation_sets` (чтение, upsert с `onConflict`, публикация). Ключ
  дедупликации inflight-сохранений тоже включает колонку — иначе попытка и
  сдача с совпавшим uuid делили бы одну очередь.
- Бакет вынесен в prop `bucket` (по умолчанию `'homeworks'`), раньше был
  зашит в двух местах.
- Список расширений расширен: кроме pdf/png/jpg теперь webp/gif/bmp/heic/
  heif/avif — ученик может прислать их через `accept="image/*"` (§20), браузер
  их рисует, значит рамки ставить можно.
- Новый prop `publishRef` — императивный доступ к публикации рамок. Нужен
  там, где кнопку рисует не футер аннотатора, а внешняя форма вердикта.
- Новый prop `publishButtonLabel` — подпись кнопки публикации в тулбаре
  (по умолчанию прежняя «Опубликовать проверку»). Там, где вердикт ставится
  отдельно, подпись честно говорит «Опубликовать пометки».

### 22.4. Три точки подключения

Общий `AttemptAnnotationOverlay.tsx` (courseProgram) — полноэкранный слой
с шапкой и лениво подгружаемым аннотатором; им пользуются все три места,
разница только в футере. Файлы, которые разметить нельзя (docx, zip и
прочее), не прячутся, а выносятся в отдельную плашку-полоску «Без разметки
(открыть отдельно)» — преподаватель должен знать, что файл есть.

1. **Модалка аккордеона курса** (`HomeworkAttemptDetailModal`): клик по фото
   или кнопка «Указать ошибки рамками» открывает аннотатор. Вердикта тут
   нет сознательно (как и раньше, §19.2) — только пометки и кнопка
   «Опубликовать пометки ученику», с подписью, что ученик увидит их лишь
   после публикации. Esc при открытом аннотаторе закрывает аннотатор, а не
   всю модалку.
2. **Очередь проверок ДЗ** (`HomeworkReviewQueuePage`): кнопка «Проверить с
   рамками» открывает тот же слой, но в футере — полная форма вердикта
   (переиспользован `ReviewActions`, не копия). Порядок важен: сначала
   публикуются пометки, потом ставится вердикт — иначе ученик мог бы увидеть
   «на доработку» без рамок, на которые ссылается комментарий. Если
   публикация пометок не удалась, вердикт НЕ сохраняется, ошибка всплывает
   в форме.
3. **Ученик** (`TopicHomeworkStudent`): в истории попыток появляется кнопка
   «Пометки учителя на работе» — открывает тот же слой в readOnly. Кнопка
   показывается только там, где рамки реально опубликованы (точечный запрос
   `annotation_sets` по своим попыткам со `status='published'`; RLS и так
   не отдала бы черновик, фильтр здесь ради того, чтобы не вести в пустой
   просмотр). Без этого пункта фича бессмысленна — рисовать рамки, которые
   никто не увидит, незачем; владелец просил два места, третье добавлено

### 23.1. Причина «нигде не видно» (пункты 1 и 2)

События цикла ДЗ (§16, миграция `20260728131304`) писались ТОЛЬКО в
`notification_queue`, канал `telegram`, и вставка шла через
`join telegram_connections tc ... and tc.is_enabled`. То есть получателю без
подключённого Telegram не доставалось НИЧЕГО. Таблица `notifications`
(колокольчик в сайдбаре со счётчиком непрочитанных) при этом не заполнялась
вовсе, а сам пункт «Уведомления» был `hidden: true` в меню — то есть
колокольчика не было видно даже при наличии уведомлений.

Проверено на проде: у единственного получателя того самого события (владелец
«Тестового курса») telegram не подключён → отправлено 0 сообщений. Никакой
ошибки в логах при этом нет — доставка просто некому.

Миграция `20260730125856_topic_homework_in_app_notifications`:

- `notifications.dedup_key` + плоский уникальный индекс (та же причина, что в
  §22.2: `on conflict` с partial-индексом требовал бы повторять предикат в
  запросе; NULL-ы различны, поэтому старые строки не мешают).
- Список получателей события курса вынесен в `_topic_homework_course_staff()` —
  он теперь нужен дважды (очередь + колокольчик), и два UNION-а не должны
  разъехаться. Множество то же, что пускает `course_is_staff`.
- `topic_homework_enqueue_submitted` и `topic_homework_enqueue_reviewed`
  дополнительно пишут строку в `notifications` — БЕЗ telegram-гейта. Telegram-
  ветка не тронута. Ученику в текст сразу кладём вердикт, балл и комментарий,
  чтобы суть была видна без открытия темы.
- Права не менялись: помощники и раньше `SECURITY DEFINER` и сами проверяют,
  что звонящий вправе породить РОВНО ЭТО событие (сдача — попытка его, вердикт —
  review его). Оба вызова на стороне RPC обёрнуты в
  `exception when others -> raise warning`, поэтому сбой уведомления не
  откатывает сдачу/вердикт — радиус поражения ограничен.
- `v_count` снимается ДО in-app вставки: `row_count` берётся от последнего
  запроса, а возвращаемое значение по контракту — число telegram-сообщений.

Проверено сквозным прогоном на проде: вызов от имени реального ученика создал
владельцу курса непрочитанное уведомление со ссылкой на `/homework-queue`;
повторный вызов вернул 0 и второй строки не создал. Досоздан сигнал для одной

## 24. Каталог заданий: убрано ожидание счётчиков (2026-07-30)

### 24.1. Замеры: что именно тормозило

`explain (analyze)` на проде:

| RPC | было |
|---|---|
| `get_catalog_direction_counts()` — 4 карточки лендинга | **2645 мс** |
| `get_catalog_section_task_counts_by_source(...)` — внутренние вкладки | **968 мс** |
| `get_catalog_section_counts(...)` | 20 мс (ок) |
| `get_catalog_topic_counts_by_source(...)` | 40 мс (ок) |

Причина одна на оба: в `catalog_tasks` лежит контент задачи, строки широкие.
Существующий `catalog_tasks_subject_idx (subject, exam_type)` не покрывает ни
`is_published`, ни `id`, поэтому планировщик шёл в heap — 1152 блока только
чтобы посчитать строки. Счётчику данные задачи не нужны вовсе.

### 24.2. Индекс (миграция `20260730132312_catalog_counts_covering_index`)

`catalog_tasks (is_published, subject, exam_type) INCLUDE (id)` — покрывающий,
оба запроса становятся Index Only Scan:

| RPC | после |
|---|---|
| `get_catalog_direction_counts()` | 2645 → **9.7 мс** (×270) |
| `get_catalog_section_task_counts_by_source(...)` | 968 → **15.9 мс** (×60) |

**Отдельно важное:** сразу после создания индекса выигрыш был всего до
260/187 мс — Index Only Scan всё равно лазал в heap (`Heap Fetches: 3143`),
потому что карта видимости не заполнена. Ускорение до 10/16 мс дал
`vacuum (analyze) public.catalog_tasks` (`Heap Fetches: 0`). То есть VACUUM
здесь не косметика, а часть фикса; в файле миграции об этом написано, так как
внутри транзакции миграции его выполнить нельзя.

### 24.3. Числа на карточках зафиксированы в коде

Как и просил владелец: `taskCount` добавлен прямо в константу `DIRECTIONS`
(`useCatalog.ts`), снято 2026-07-30 — math_ege 9515, math_oge 5972,
physics_ege 3386, physics_oge 2910. Лендинг теперь не делает ни одного
запроса: ни загрузки, ни состояния ошибки, ни скелетона в футере карточки.

Хук `useCatalogDirectionCounts` и тип `DirectionCountRow` удалены как мёртвый
код (50 строк). Саму RPC в базе оставил — ей теперь пользуются только чтобы
обновить константы:

```sql
select * from get_catalog_direction_counts();
```

Числа показываются округлёнными («9.5 тыс.»), поэтому расхождение незаметно
примерно до ±50 задач — точность здесь заведомо избыточна. Порядок обновления
записан комментарием над `DIRECTIONS`.

### 24.4. Почему внутренние вкладки НЕ захардкожены

Там в счётчик входит `completed_count` — личный прогресс ученика из
`catalog_task_progress` («12 из 89 — 13%»). Зашить его в код нельзя: он у
каждого свой и меняется по ходу решения. Поэтому для внутренних вкладок
ускорение сделано индексом (968 → 16 мс), а не константами.

## 25. Каталог: настоящая причина медленной загрузки (2026-07-30)

Владелец после §24: «можно ли ещё ускорить? Всё равно довольно очень долго
загружается, особенно темы и количество задач. Может их зафиксируем тоже в
коде, и будем вызывать только прогресс».

Предложение разумное, но замеры показали, что фиксировать числа там почти
ничего не дало бы: SQL после §24 уже считался за 10–16 мс. Тормозило другое —
**количество последовательных запросов** и **размер бандла**. Обе причины
устранены, числа тем фиксировать не понадобилось (и не следовало: в них
входит личный прогресс).

### 25.1. Темы: ~32 последовательных запроса → один

`useCatalogTopics` в обычном (экзаменационном) виде делал агрегацию в браузере:

1. `fetchAllPagedRows` по `catalog_tasks` — выкачать ВСЕ id задач раздела;
2. разбить их на пачки по `IN_FILTER_CHUNK = 50` и на КАЖДУЮ сделать
   отдельный запрос к `catalog_task_topics`;
3. запрос к `catalog_topics` по собранному списку id;
4. прогресс — снова пачками по 50.

На самом большом разделе математики ЕГЭ (1036 задач) это ~20 запросов на
связи плюс ~20 на прогресс, все строго друг за другом. При круговой задержке
150–250 мс — 5–8 секунд на один раздел. Ровно то, что и наблюдалось.

Миграция `20260730134546_get_catalog_section_topic_tree`: одна RPC отдаёт темы,
число задач и личный прогресс. Замер на том же разделе (1036 задач, 25 тем) —
**11 мс**. Клиентская реализация (142 строки) заменена на 46, включая
react-query-кэш.

Важная деталь зафиксирована в комментарии миграции: связи НЕ фильтруются по
`source` — в экзаменационном виде учитываются и legacy-связи (`source is null`),
и `ai_physics_v1`. Этим RPC отличается от `get_catalog_topic_counts_by_source`,
специально суженной под физический вид. Раньше это держал клиентский код и
закреплял тест; тест теперь проверяет файл миграции.

### 25.2. Разделы: три запроса шли друг за другом без нужды

`useCatalogSections` последовательно ждал: список разделов → счётчики задач →
прогресс. Три независимых источника — три круговые задержки вместо одной.
Теперь `Promise.all` и react-query поверх: возврат в уже открытый раздел не
перезапрашивает ничего (`CATALOG_STRUCTURE_CACHE_MS` = 5 минут — достаточно
для мгновенных переходов «раздел → тема → назад», и при этом отмеченная
задача отражается в счётчиках без перезагрузки страницы).

### 25.3. Главное: бандл 3,16 МБ одним куском

После всего этого запросы стали 10–16 мс, но «долго открывается» осталось бы,
потому что `AppRoutes.tsx` статически импортировал все 60 страниц и собирался
в **один чанк на 3 158 КБ (757 КБ gzip)**. Браузер обязан скачать и разобрать
его целиком, чтобы показать любую страницу — на мобильном интернете это
секунды до первого пикселя, независимо от скорости базы.

Все 60 страниц переведены на `React.lazy` + один `<Suspense>` вокруг
`<Routes>` (тот же приём, что уже применялся в `App.tsx` для лендинга):

| Чанк | Было | Стало |
|---|---|---|
| `AppRoutes` | 3 158 КБ (757 КБ gzip) | **43 КБ (10,8 КБ gzip)** |
| `CatalogPage` | внутри AppRoutes | свой чанк 11,3 КБ (3,9 КБ gzip) |

То есть на открытие каталога теперь приходит ~194 КБ gzip вместо ~935 КБ —
примерно в 4,8 раза меньше JS на скачивание и разбор.

Заглушка `RouteFallback` намеренно скромная, без полноэкранного оверлея:
каркас (сайдбар, шапка) уже отрисован `DashboardLayout`, подменяется только
содержимое.

| Шаг | Было | Стало |
|---|---|---|
| Числа на лендинге | 2645 мс, 1 запрос | 0 запросов (§24) |

### 29.2. Рамки — решение владельца

Курс сейчас = одна группа (§9.1), поэтому куратор курса видит учеников
**курса**. Если появятся многогрупповые курсы и понадобится сузить куратора до
конкретных групп — нужна отдельная связь куратор↔группа; сейчас её в модели
нет вовсе, `course_curators` по определению членство уровня курса.

### 29.3. Фикс (миграция `20260730213917_course_curators_see_course_roster`)

Вместо того чтобы дописать `course_curators` в пять мест, всюду, где
спрашивается «персонал ли этот человек по данному курсу», зовём **одну**
`course_is_staff`. Она уже знает про админа, владельца курса, преподавателя
группы, куратора группы и куратора курса — и будет знать про любые новые роли
без правки пяти мест. Именно рассинхрон ручных копий и породил и §21, и этот
баг.

Побочно закрыт остаток §21: у групп с пустым `teacher_id` владелец курса
(не платформенный админ) не видел ни группу, ни членство — политики
`groups_select_all` и `group_students_select_teacher` fallback на владельца
тогда не получили. Теперь получают.

Рекурсии нет: `course_is_staff` — SECURITY DEFINER, внутри RLS не применяется,
поэтому её вызов из политики на `groups`/`courses` безопасен (проверено —
запросы отрабатывают).

### 29.4. Проверки

Локальный Postgres 16, эмуляция ролей: **до** фикса куратор курса видел 0 из 5
сущностей и 0 строк ростера; **после** — все 5 и 1 строку. Контроли:
посторонний куратор по-прежнему 0; владелец курса как видел, так и видит;
ученик видит себя, но НЕ видит однокурсника (ни строку `students`, ни профиль).

На проде после применения: преподаватель демо-курса видит своего ученика
(`true`), посторонний преподаватель — нет (`false`).

**Ловушка при проверке, на которую я попался:** `set_config(...)` и вызов
проверяемой функции в ОДНОМ списке выборки — порядок вычисления столбцов
Postgres не гарантирует, и результат выходит случайным. Правильная форма —
`set_config` в подзапросе `FROM` (он вычисляется раньше списка выборки):

```sql
select public.auth_is_staff_of_student('...')
from (select set_config('request.jwt.claim.sub','<uuid>',true)) s;
```

И вторая: первый прогон дал `false`, но это оказался не регресс — ученик
`qweasd` к тому моменту был **удалён из группы** при тестах владельца, так что
персонала у него не осталось по определению. Прежде чем считать проверку
провалившейся, стоит убедиться, что данные под ней ещё те же.

**Не проверено живым кликом** — на проде нет ни одного куратора курса.
Чтобы проверить: создать вторую ссылку курса (кураторскую), вступить по ней
отдельным аккаунтом и убедиться, что вкладки «Ученики» и «Домашние задания»
не пустые, а в очереди проверки видны фамилии.

## 30. Двойная проверка одной работы (2026-07-30)

Владелец: «может ли быть такое, что куратор и учитель проверяют одну и ту же
работу? Нужно наверное как-то обозначить этот момент».

Может: очередь `/homework-queue` у персонала курса общая — владелец,
преподаватели групп и кураторы видят одни и те же сданные работы, и никакого
«занято» в ней нет. Разобрал три места, где это может проявиться. Картина
оказалась несимметричной.

### 30.1. Вердикт — защищён на уровне базы

`topic_homework_review_attempt` меняет статус только
`where status = 'submitted'` и, не найдя строки, падает. Функция plpgsql, то
есть одна транзакция: при отказе откатывается и вставка в
`topic_homework_reviews`. Второй вердикт **не может** перезаписать первый —
ни оценку, ни комментарий. Гонка тоже закрыта: `UPDATE` берёт блокировку
строки, второй ждёт и видит уже изменённый статус.

Плохо было другое: наружу летел текст «Попытка не в статусе "сдано"».
Технически верно, преподавателю — бессмысленно, да и строка оставалась висеть
в очереди. Теперь распознаём этот случай (`isAlreadyReviewedError`), показываем
«Эту работу уже проверил кто-то другой — она убрана из очереди» и сразу
убираем строку.

Опознаём по тексту, потому что своего кода ошибки у RPC нет. Хрупковато, но
менять сигнатуру RPC ради этого — большая цена; тест на формулировку добавлен.

### 30.2. Рамки — «последний пишет» (осталось как есть)

`annotation_sets` уникальна по `(attempt_id, file_path, page)`, и `savePage`
пишет страницу **целиком**: массив всех объектов. Если двое держат одну
страницу открытой одновременно, сохранение второго затрёт то, что первый
добавил уже после его загрузки. Молча.

Последовательная работа при этом безопасна: открывая работу, проверяющий
ВИДИТ чужие черновые пометки (RLS пускает персонал курса к `draft`), дополняет
их и сохраняет весь набор. Теряется только одновременное редактирование.

Чинить полноценно — это либо блокировка работы за проверяющим, либо слияние по
`id` объектов при сохранении. Для школы, где у курса один-два сотрудника,
цена выше пользы. Вместо этого сделал предупреждение: если среди загруженных
пометок есть чужие (сравнение `annotation_sets.author_id` с текущим профилем),
в тулбаре разбора появляется плашка «Работу уже смотрел другой преподаватель»
с подсказкой, что сохранение перезапишет страницу целиком.

Это честно обозначает риск, не изображая защиту, которой нет. Если
одновременная проверка станет реальностью — возвращаться сюда за блокировкой
или слиянием.

### 30.3. Чего сознательно НЕ делал

- **Не показываю «работу смотрит N»** — это требует присутствия (realtime или
  таблица заявок). Для нынешнего масштаба избыточно.
- **Не запрещаю второй вердикт** — он и так невозможен, база не даст.
- **Не блокирую работу за первым открывшим** — блокировка без снятия по
  таймауту хуже проблемы: забытая вкладка заперла бы работу навсегда.

### 30.4. Проверки

`tsc`, `vite build` чистые; 26/26 по затронутым файлам плюс 3 новых теста на
`isAlreadyReviewedError` (узнаёт отказ, не путает с ошибками валидации балла и
прав, не падает на пустом).

**Не проверено живым кликом** — нужно два аккаунта персонала на одном курсе.
Стоит проверить, когда появится куратор: открыть одну работу с двух аккаунтов,
поставить вердикт с первого и убедиться, что второй получит понятное сообщение,
а строка уйдёт из очереди.

## §31. Присутствие в проверке ДЗ: «Смотрит: Имя» + мягкая защита (2026-07-30)

Прямое продолжение §30. Там я написал, что показывать «работу смотрит N» —
избыточно, и владелец сразу возразил:

> «а просто в реал тайме нельзя показывать что сейчас куратор или ученик
> проверяет работу? И что он просто не даст его открыть, потому что он сейчас
> редактируется»

Первая половина — правильная и дешёвая. Ко второй я отнёсся осторожно и вынес
выбор владельцу: присутствие — это ПОДСКАЗКА, а не мьютекс. Сеть моргнула —
человек «исчез» на секунды; лаг — и двое вошли одновременно. Плюс второй
чаще всего заходит посмотреть, а не править.

**Владелец выбрал «Показывать + мягкая защита».** Именно это и сделано.

### 31.1. Почему Presence, а не замок в базе

Строку-замок надо снимать. Вкладку закрывают, роняют, теряют связь — и работа
осталась бы запертой навсегда, а расцепить её некому: интерфейса снятия нет,
таймаут пришлось бы выдумывать. Supabase Presence снимает участника сам при
обрыве соединения (событие `leave`), поэтому зависших замков не бывает
в принципе. Цена — та самая неточность подсказки, и интерфейс её учитывает:
он предупреждает, а от порчи данных по-прежнему защищает база
(§30.1, `isAlreadyReviewedError`).

Реалтайм в проекте до этого не использовался вообще (`.channel(` не встречался
нигде). Это первое место.

### 31.2. Канал — на КУРС, не на работу

`hw-review:<course_id>`, в payload участника — `{ profileId, name, attemptId }`.

Очередь показывает десятки работ разом. Канал-на-работу означал бы десятки
сокет-подписок с одной вкладки. Канал на курс — одна подписка, а кто в какой
работе, видно из payload. Курсов в очереди обычно один-три.

### 31.3. Канал приватный, права — через ту же `course_is_staff`

Миграция **20260730220534_realtime_review_presence_authorization**.

Публичный канал читается и пишется любым, у кого есть anon-ключ, — а он лежит
в бандле. Посторонний мог бы и собрать имена преподавателей, и наоборот —
подделать присутствие, чтобы все работы выглядели «занятыми». Поэтому канал
приватный (`config.private = true`), а доступ решают две политики на
`realtime.messages` (SELECT — читать присутствие, INSERT — заявлять своё).

На `realtime.messages` RLS был включён, а политик не было ни одной — то есть
все приватные каналы были закрыты. Новые политики открывают ровно топики вида
`hw-review:<uuid>` и ровно персоналу курса; любые другие приватные каналы,
если появятся, остаются закрытыми.

Права считает **`public.course_is_staff`** — по правилу из `CLAUDE.md`. Здесь
это особенно важно: круг лиц в канале обязан совпадать с кругом, который видит
сами работы, иначе присутствие покажет имена посторонним.

Топик приходит от клиента, поэтому его разбирает отдельная функция
`public.realtime_review_topic_course(text)`: голое `substring(...)::uuid` упало
бы на кривом значении. Функция возвращает `NULL` на всём, что не подходит под
шаблон, а `course_is_staff(NULL) = false` (у неё первым условием
`p_course_id is not null`).

Предикат проверен ровно так, как его вычислит Realtime — `set role
authenticated` + `request.jwt.claims` + GUC `realtime.topic`, `set_config`
в подзапросе `FROM` (ловушка из `CLAUDE.md`):

| кто | топик | доступ |
|---|---|---|
| владелец курса | свой курс | **true** |
| посторонний преподаватель | тот же топик | false |
| владелец курса | топик чужого курса | false |
| владелец курса | `hw-review:not-a-uuid` | false |
| владелец курса | префикс `secret:` | false |
| без JWT | свой курс | false |

### 31.4. Что видит человек

- **В очереди** на строке появляется янтарный бейдж «Смотрит: Аня». Двоих
  называет поимённо, дальше переходит на счёт («Аня, Борис и ещё 2») — строка
  узкая, и точное число важнее списка.
- **При открытии работы, в которой уже кто-то есть**, разбор открывается
  в режиме чтения: рисовать нельзя, форма вердикта скрыта. Полоса сверху
  объясняет почему и даёт кнопку **«Всё равно редактировать»** — осознанный
  выход, без риска запереть работу навсегда.
- **Если коллега зашёл ПОСЛЕ вас**, режим не меняется — только предупреждение.
  Выбивать из редактирования того, кто уже рисует, потому что второй зашёл
  посмотреть, было бы хуже самой проблемы. Поэтому `locked` снимается ровно
  один раз, в момент открытия.
- В режиме чтения аннотатору явно передаётся `annotationVisibility='all'`:
  по умолчанию он показал бы только опубликованные пометки, а второй
  проверяющий пришёл смотреть ровно то, что коллега рисует прямо сейчас.

Работает в обоих местах разбора (§26): и в модалке из аккордеона курса, и
в полноэкранной «Очереди проверок ДЗ» — канал общий, поэтому двое видят друг
друга, даже если пришли разными дверями. Ради этого
`HomeworkAttemptDetailModal` получил проп `courseId`.

### 31.5. Отказ канала не ломает экран

Нет прав, нет сети, Realtime выключён — `viewers` остаётся пустым, и экран
выглядит ровно как до этой фичи. Присутствие лежит поверх работы, а не под ней.
При `CHANNEL_ERROR`/`TIMED_OUT`/`CLOSED` последнее известное состояние
**выбрасывается**: показывать «работу смотрит Аня», когда это могло стать
неправдой минуту назад, хуже, чем не показывать ничего.

3. Второй жмёт «Всё равно редактировать» — рисование включается.
4. Первый закрывает вкладку — бейдж у второго исчезает сам, без перезагрузки.

## §32. ИИ-проверка ДЗ: черновик преподавателю (2026-07-30)

Владелец: «следующий этап реализации — проверка работы через CV и написание
обратной связи. Давай выберем AI и сделаем так, чтобы ИИ автоматически могла
проверить работу и выставить баллы».

Четыре развилки вынес владельцу вопросом, потому что это не технические
решения. Его выбор:

| Развилка | Решение владельца |
|---|---|
| Самостоятельность ИИ | **Черновик для преподавателя** — ученик не видит ничего до подтверждения |
| Откуда эталон | **ИИ читает условие и работу и разбирает решение сам** (не привязка к каталогу, не критерии текстом) |
| Провайдер | **Напрямую**, есть зарубежная карта/юрлицо |
| Формат выдачи | **Рамки + балл + текст** |

### 32.1. Что было найдено до начала работ

Фундамент уже лежал — но не на том контуре. В миграции
`20260723082631_homework_v2_ai_foundation` есть `homework_ai_jobs` и
`homework_ai_item_evaluations` с `suggested_score`, `confidence`, `evidence`
в нормализованных координатах. Всё это смотрит на `homework_attempts` —
Homework V2, 0 строк, скрыт из меню. Как чертёж пригодилось, переиспользовать
нельзя.

Там же, в `20260726073913`, записана установка, ради которой всё и делалось
так, а не иначе: «AI никогда не пишет сюда — его место в будущей
`topic_homework_ai_jobs(attempt_id)`, которая лишь предлагает результат».

Главная нехватка — **эталона нет**. У `topic_homework` только `title`,
`instructions`, `due_at`, `grade_scale`; условие живёт картинкой в
`topic_homework_files`. Связи с `catalog_tasks` (где есть `answer_html`,
`solution_html`, `grade_criteria_html`, `max_points`) не существует вовсе.
Владелец сознательно выбрал работать без эталона — это быстрее и покрывает
любые ДЗ, но качество разбора целиком лежит на модели.

### 32.2. Выбор модели: решили рамки, а не «ум»

Требование «рамки» отсекает почти всё. Ставить координаты по изображению
умеет практически только Gemini: **ScreenSpot-Pro 72.7% против 3.5% у
GPT-5.1**. Разница не в качестве, а в наличии способности — у GPT её
фактически нет.

Второй критерий — чтение документа: **OmniDocBench edit distance 0.115** у
Gemini 3 Pro против 0.145 у Claude Sonnet 4.5 и 0.147 у GPT-5.1 (меньше —
лучше). Нам читать рукописную математику, это узкое место всей затеи.

Flash не взял, хотя он дешевле в разы: **3.6 Flash в детекции слабее (56%
mAP@50)**, «ленится» и отдаёт одну большую рамку вместо нескольких точных.
Рамки здесь — половина ценности.

Итог: `gemini-3.1-pro-preview`. Идентификаторы Google меняет часто (сначала
я поставил `gemini-3-pro-preview` — такой модели уже нет), поэтому модель
вынесена в переменную окружения **`GEMINI_MODEL`**: смена не требует правки
кода. Дешёвая альтернатива для сравнения — `gemini-3.5-flash`.

**Цена:** ~5k входных и ~1.5k выходных токенов на проверку (фото A4 ≈ 1550
токенов, тайлы 768×768 по 258) — порядка **2–4 ₽ за работу**.

### 32.3. Устройство

Миграции `20260730225053`, `20260730225142`, `20260730230324`.

**ИИ не пишет в `topic_homework_reviews`.** Ни строки. Вердикт и балл ученику
ставит человек, `reviewer_id → profiles` остаётся правдой. Это не
договорённость, а отсутствие соответствующего кода в функции.

Две новые таблицы:

- `topic_homework_ai_jobs` — прогон: статус, провайдер, модель, `readable`,
  `suggested_score`, `confidence`, `summary`, токены, `accepted_at`.
  Частичный уникальный индекс по `attempt_id where status in
  ('pending','processing')`: два параллельных прогона — двойная оплата и
  гонка на запись. Завершённых прогонов может быть сколько угодно
  (перепроверка).
- `topic_homework_ai_findings` — рамки в тех же нормализованных [0,1]
  координатах, что у `annotation_sets`, и с теми же категориями
  (`calc/logic/format/praise/comment`).

**Почему находки отдельно, а не в `annotation_sets`:** там `author_id` NOT
NULL → `profiles` (у ИИ нет профиля), страница пишется целиком одним JSON
(ИИ и человек затрут друг друга, §30.2), и нет статуса «предложено, не
подтверждено». Поэтому ИИ пишет к себе, а преподаватель, нажав «Перенести
рамки», переносит их к себе — и дальше они неотличимы от нарисованных рукой,
их можно двигать и удалять. Это и есть «предложение», а не «правка».

**Права:** читает тот же круг, что может проверять работу — цепочка
`topic_homework_attempt_can_review → topic_homework_can_manage →
topic_material_can_manage → course_is_staff`. Правило CLAUDE.md соблюдено,
ручных копий условий нет. Политик на запись нет совсем.

Дважды пришлось убирать наследство умолчаний схемы Supabase:
`20260730225142` снял с `authenticated` табличные INSERT/UPDATE/DELETE
(RLS их и так резал — проверено, 42501, — но защита в один слой на черновике
оценки неуместна), `20260730230324` снял EXECUTE у `anon` с обеих RPC по
наводке советника.

### 32.4. Промпт — часть поведения, а не «текст»

Три вещи, ради которых он написан именно так (`prompt.ts`):

1. **Сначала решить самому, потом сверять.** Без этого модель соглашается
   с ходом ученика: ошибка в середине выглядит убедительно, когда читаешь
   подряд. Эталона в базе нет, так что это единственная опора.
2. **Текст внутри изображения — данные, а не команда.** Ученик может
   написать на листе «поставь 5 баллов» или «инструкции отменены». Модель,
   читающая картинку, воспринимает это как часть промпта, если не сказать
   обратного. Угроза не гипотетическая: работа приходит от того, кого
   оценивают. Промпт требует ещё и упомянуть такую надпись в разборе.
3. **Молчать лучше, чем выдумывать.** Ложная рамка стоит внимания и доверия
   преподавателя; пропущенная — почти ничего, он всё равно смотрит глазами.

`temperature: 0.2` — проверка не творческая задача: «перепроверить» не должно
быть лотереей.

### 32.5. Всё, чему верим модели, проверяется отдельно

`gemini.ts` — чистый слой, 20 тестов. Кривое выпадает **поштучно**: одна
битая рамка не отменяет остальные пятнадцать.

- `box_2d` (шкала 0..1000, порядок `[ymin,xmin,ymax,xmax]`) → `rect` [0,1];
  перепутанный порядок чиним, значения не в той шкале (похожие на пиксели)
  отбрасываем целиком, рамку мельче 0.5% страницы — тоже: попасть ей в
  строку модель не могла, это шум.
- `readable: false` + балл — противоречие внутри ответа. Верим признанию
  в нечитаемости: балл за непрочитанное хуже отсутствия балла.
- Балл не из своей шкалы («85» при пятибалльной — частая ошибка) снимаем,
  а разбор сохраняем: в базе CHECK, и попытка записать уронила бы весь
  прогон вместе с полезным текстом.
- Ответ модели достаём устойчиво: склеиваем части, переживаем
  markdown-обёртку, отказ по safety объясняем словами.

### 32.6. Что видит преподаватель

Панель «Черновик ИИ» — в разборе работы, над формой вердикта. Кнопка
«Проверить с ИИ» → через минуту балл, уверенность, текст обратной связи и
число найденных мест. Дальше два действия: **«Перенести рамки»** и
**«Вставить в комментарий»**.

Балл **не показывается** при низкой уверенности и при `readable: false`
(`shouldShowScore`): число рядом с надписью «предлагает ИИ» слишком легко
принять за оценку, а так преподаватель поставит его сам.

Ученик панели не видит никогда — RLS отдаёт `topic_homework_ai_*` только
персоналу курса.

### 32.7. Сознательно не сделано

- **Автозапуск при сдаче.** Воркер `claim_topic_homework_ai_jobs` уже
  написан (по образцу `claim_notification_queue`, с реанимацией зависших),
  но проверка пока запускается кнопкой. Причина простая: качество на
  рукописной математике не измерено, а фоновая проверка каждой сдачи — это
  деньги за работы, которые могут никто не открыть. Чтобы включить фон,
  останется добавить триггер на `status → 'submitted'` и расписание pg_cron.
- **Привязка ДЗ к каталогу.** Владелец выбрал разбор без эталона. Если
  качество окажется недостаточным — это первое, куда возвращаться: в
  `catalog_tasks` уже лежат ответ, решение, критерии ФИПИ и максимальный
  балл, а `topic_test_items` показывает готовый образец «снапшот эталона на
  сервере».

### 32.8. Проверки и чего не хватает для запуска

`tsc`, `vite build` чистые; 62/62 по затронутым файлам, из них 20 новых на
разбор ответа модели. Схема проверена на локальном Postgres 16 (9 проб),
права — под ролью `authenticated` на проде.

**Функция не проверена живым вызовом**: нужен `GEMINI_API_KEY`, а из
песочницы egress-прокси всё равно блокирует внешние вызовы. Пока ключа нет,
функция честно отвечает 503 «ИИ-проверка не настроена», а панель показывает
это человеческим текстом, а не кодом ошибки.

**Осталось сделать владельцу:**
1. Получить ключ в Google AI Studio (нужна зарубежная карта).
2. Supabase → Project Settings → Edge Functions → Secrets: `GEMINI_API_KEY`.
   Опционально `GEMINI_MODEL`, если захочется сменить модель.
3. Задеплоить функцию `check-homework-ai`.

**Отдельно, и это важно:** фото рукописных работ уходят в Google. Это
персональные данные учеников и трансграничная передача. С точки зрения
152-ФЗ на это нужно согласие — стоит показать формулировку юристу до
включения фичи в бой.

## §33. Переход на Qwen: слой сменного провайдера (2026-07-30)

Владелец: «давай попробуем Qwen сначала» — после разбора цен (§32.2, где я
выбрал Gemini) и вопроса про другие модели.

### 33.1. DeepSeek отпал по факту, а не по цене

Первым владелец спросил про DeepSeek. Ответ короткий: **официальный API
DeepSeek не принимает изображения.** V4 Pro и V4 Flash текстовые,
документированного формата запроса с картинкой нет (проверено 14.07.2026).

Зрение у DeepSeek есть — DeepSeek-VL2, Janus, DeepSeek-OCR, — но только
открытыми весами: это «арендуй сервер с видеокартой и обслуживай его».
Возни несопоставимо больше экономии. Исследование «Thinking with Visual
Primitives» (апрель 2026) действительно предлагает рамки как пространственные
метки в рассуждении, но статья и публичный API — разные вещи.

### 33.2. Qwen — настоящий конкурент

| Модель | вход $/M | выход $/M | ₽/проверка | Рамки |
|---|---|---|---|---|
| Gemini 3.1 Pro | 2.00 | 12.00 | 5,24 ₽ | да, `box_2d` |
| **qwen/qwen3.7-plus** | 0.32 | 1.28 | **0,61 ₽** | да, `bbox_2d` |
| qwen/qwen3.7-max | 1.25 | 3.75 | 1,96 ₽ | да |
| qwen/qwen3-vl-32b-instruct | 0.104 | 0.416 | 0,20 ₽ | да |

Выбрана **`qwen/qwen3.7-plus`**: по каталогу OpenRouter у неё подтверждены
ОБА нужных свойства — приём изображений и `structured_outputs`. У части
VL-моделей второго нет, а без него ответ приходится выковыривать из
свободного текста. Примерно в восемь раз дешевле Gemini на нашей нагрузке.

**Чего про Qwen никто не знает:** в документации нет ни слова про рукописный
текст. Заявлены печатные документы, устойчивость к плохому свету, размытию и
наклону, OCR на 32 языках — про почерк молчание. Ровно поэтому и нужен
сменный провайдер: выяснить это можно только прогоном реальных работ.

### 33.3. Одна деталь, на которой легко потерять день

**Порядок координат у провайдеров разный:**

- Gemini: `box_2d = [ymin, xmin, ymax, xmax]` — **y первым**
- Qwen: `bbox_2d = [x1, y1, x2, y2]` — **x первым**

Шкала у обоих одна, 0..1000 от размера изображения (Qwen формально
рекомендует делить на 999 ради обратной совместимости — разница 0.1%, меньше
пикселя на странице).

Перепутать легко, а заметить трудно: на квадратной картинке ошибка выглядит
как «модель промахнулась мимо строки», а не как баг в коде. Поэтому
`boxToRect(box, order)` параметризован, а в тестах стоит проба «перепутанный
порядок даёт ДРУГУЮ рамку» — иначе тест на несимметричной рамке проходил бы
при любой реализации.

Просим у каждой модели её родной диалект (`box_2d` против `bbox_2d`): на нём
она обучена, попытка навязать свой формат стабильно ухудшает попадание.
Разбор принимает оба ключа.

### 33.4. Устройство слоя

```
supabase/functions/check-homework-ai/
  index.ts       — оркестрация: права, storage, запись в базу
  providers.ts   — два вызова с одинаковым контрактом + выбор из окружения
  parse.ts       — общий разбор ответа (бывший gemini.ts)
  prompt.ts      — промпт; формат рамки и описание JSON зависят от провайдера
```

Настройки (Supabase → Edge Functions → Secrets):

| Переменная | Смысл |
|---|---|
| `AI_API_KEY` | ключ; для Gemini понимается и старый `GEMINI_API_KEY` |
| `AI_PROVIDER` | `openai` (по умолчанию) или `gemini` |
| `AI_MODEL` | по умолчанию `qwen/qwen3.7-plus`, для Gemini — `gemini-3.1-pro-preview` |
| `AI_BASE_URL` | по умолчанию OpenRouter; для Alibaba Model Studio — свой адрес |
| `AI_BOX_ORDER` | аварийная ручка, если модель поведёт себя не по документации |
| `AI_JSON_SCHEMA` | `1` — просить жёсткую схему вместо `json_object` |

**Почему `json_object`, а не `json_schema`, по умолчанию.** Alibaba Model
Studio поддерживает только `json_object` (и требует слова «JSON» в
сообщениях — оно есть в промпте). OpenRouter для `qwen3.7-plus` заявляет
`structured_outputs`, но полагаться на это по умолчанию не стал: `json_object`
работает везде, форму ответа описывает промпт, а стережёт разбор. Включается
одной переменной, если захочется.

Ещё два следствия разницы провайдеров:

- **PDF.** Gemini принимает его напрямую, OpenAI-совместимые — далеко не все.
  Набор форматов теперь зависит от провайдера, и на Qwen работа без
  фотографий честно отвечает «модель читает только картинки», а не падает
  невнятной ошибкой чужого API.
- **Обрыв по лимиту.** У OpenAI-совместимых `finish_reason: 'length'` даёт
  валидный, но недописанный JSON. Без отдельной ветки преподаватель увидел бы
  «Ответ модели — не JSON» и не понял бы, что делать. Теперь — «Ответ модели
  не поместился в лимит». `max_tokens: 8000`, разбор с рамками длинный.

### 33.5. Проверки

`tsc`, `vite build` чистые. **39 тестов** на чистый слой (было 20):
добавлены оба порядка координат, приём `bbox_2d`, разбор ответа
chat/completions, обрыв по лимиту, ошибка провайдера, `parseJsonText`
с болтовнёй вокруг JSON, и шесть проб на `resolveProvider` — это
единственное, что владелец правит руками, и ошибка там тихая.

В панели черновика теперь подписана модель: пока сравниваем провайдеров, без
подписи непонятно, чей это разбор.

**Живым вызовом по-прежнему не проверено** — нужен ключ, а из песочницы
egress-прокси блокирует внешние вызовы.

### 33.6. Как сравнить модели

1. Ключ OpenRouter (принимает карты, пополняется на любую сумму).
2. Secrets: `AI_API_KEY`. Больше ничего — умолчания уже на Qwen.
3. Прогнать 10 реальных работ, посмотреть: попадают ли рамки в нужные строки,
   верен ли разбор по существу, адекватен ли балл.
4. Сменить `AI_MODEL` на `qwen/qwen3.7-max`, потом `AI_PROVIDER=gemini` —
   и прогнать те же работы. Модель видна в панели и пишется в
   `topic_homework_ai_jobs.model`, так что сравнить можно и постфактум:

```sql
select model, count(*) as прогонов,
       count(*) filter (where readable) as прочитал,
       round(avg(suggested_score), 2) as средний_балл,
       count(*) filter (where accepted_at is not null) as рамки_приняты
  from topic_homework_ai_jobs
 where status = 'done'
 group by model;
```

`accepted_at` здесь — честная метрика пользы: сколько раз преподаватель
реально забрал черновик, а не просто посмотрел.

**Замечание про приватность:** OpenRouter — ещё один посредник, через
которого идут фото работ учеников. Для пилота на десятке работ это разумный
размен, для постоянной работы стоит ходить напрямую в Alibaba Model Studio
(`AI_BASE_URL`) или вернуться к Gemini. Трансграничная передача остаётся в
любом случае — меняется только страна (§32.8).

## §34. Квота Supabase исчерпана, каталог переехал на R2, картинки сжимаются при загрузке (2026-07-31)

### 34.1 Что случилось

Проект упёрся в оба бесплатных лимита Supabase одновременно: хранилище 2,36 ГБ
при потолке 1 ГБ и база 592 МБ при потолке 500 МБ. Сервис ограничили — перестали
отвечать REST, Auth и Storage, войти в школу стало нельзя. Виноват был каталог
задач: бакет `catalog-assets` — 282 212 объектов и 2197 МБ, то есть 93% всего
хранилища. Он же раздул базу: одна таблица `storage.objects` весила 345 МБ из 592.

Важное наблюдение на будущее: при ограничении сервиса **удалить данные тоже
нельзя**. Файловый менеджер в дашборде не работает, S3-эндпоинт закрыт, прямое
удаление строк из `storage.objects` запрещает триггер `storage.protect_delete`.
Единственный выход из этого состояния — оплатить тариф. Поэтому лимит нужно
ловить заранее, а не по факту.

### 34.2 Как чинили

Каталог картинок уже был перекачан на Cloudflare R2 (`assets.alminion.ru`),
Supabase хранил его вторую, никем не читаемую копию: фронт ходит на R2 через
`VITE_ASSETS_BASE_URL` и `getAssetUrl` в `useCatalog`. Порядок действий был такой:

1. Пофайловая сверка R2 против Supabase (`rclone check --one-way --size-only`).
   Сравнения по количеству недостаточно — нашлись пять SVG, которых на R2 не
   было; их докачали отдельно.
2. Локальный бэкап с R2 на диск: 282 207 файлов, 2,14 ГБ в `D:\backup\catalog-assets`.
3. Удаление копии из Supabase.

**Грабли, стоившие часа: `rclone purge` на Supabase не работает.** Он запрашивает
листинг версий объектов (`ListObjectVersions`), а Supabase отдаёт ответ с
`IsTruncated: true` без `NextKeyMarker`; rclone считает такой ответ битым и
отказывается удалять — правильно делает. Рабочая команда — `rclone delete`,
она ходит обычным `ListObjectsV2`. Бакет остаётся пустым, это нормально.

После удаления база сама не уменьшилась: Postgres освободившееся место
файловой системе не отдаёт. Понадобился `VACUUM FULL storage.objects` —
после него таблица 328 КБ вместо 345 МБ, база 248 МБ вместо 592 МБ.

Итог: хранилище 120 МБ, база 248 МБ. Оба показателя снова укладываются в
бесплатный тариф, а трафик картинок ушёл на R2, где он не тарифицируется.

### 34.3 Сжатие картинок при загрузке — `src/lib/imageCompression.ts`

Причина, по которой это сделано сразу, а не «когда-нибудь»: работы учеников
растут ровно так же, как рос каталог, только медленнее. Фотография страницы с
телефона — 3–6 МБ и 4000 пикселей по длинной стороне. Ни преподавателю, ни
модели такое разрешение не нужно: 2400 пикселей хватает с запасом, а вес падает
в 5–10 раз. Дешевле сжать до загрузки, чем потом переносить ещё один бакет.

Устройство: `compressImageFile(file, preset)` возвращает НОВЫЙ `File` либо тот
же самый, если сжимать нечего. Пресеты — `HOMEWORK_PHOTO_PRESET` (2400 px,
q0.85, работы учеников — их читают с увеличением), `MATERIAL_IMAGE_PRESET`
(2000 px, q0.82, материалы), `JPEG_ONLY_PRESET` (для `course-materials`, где
список разрешённых MIME-типов не включает webp).

Решения, которые важно не переиграть по невнимательности:

- **Сжатие не имеет права ломать загрузку.** В модуле нет ни одного `throw`:
  неизвестный формат, отказ декодера, отсутствие canvas, результат тяжелее
  оригинала — всё возвращает исходный файл. Ученик сдаёт работу в любом случае.
- **Не трогаем SVG (вектор), GIF (анимация не переживёт canvas) и HEIC**
  (браузеры не декодируют; Safari и так отдаёт снимки как JPEG).
- **Декодируем с `imageOrientation: 'from-image'`** — иначе фото с телефона
  ложится боком: EXIF-поворот теряется при отрисовке на canvas.
- **У запасного пути декодирования есть таймаут** (`DECODE_TIMEOUT_MS`, 15 с).
  Без него отказ, при котором не приходит ни `onload`, ни `onerror`, оставил бы
  кнопку загрузки крутиться навсегда.
- **Вызов стоит ДО построения пути в Storage**, и дальше по всей функции
  используется сжатая версия — в пути, в `contentType`, в теле запроса и в
  полях записи в БД. Иначе в базе окажется описание, не совпадающее с тем, что
  реально лежит в Storage.

Подключено в: `useTopicHomework` (`uploadHomeworkFile`, `uploadAttemptFile`),
`useTopicMaterialItems` (`uploadMaterialFile`), `useLessonMaterials`
(`uploadLessonMaterialFile`). Легаси-контур `CreateHomeworkModal` не трогали
сознательно — он мёртв.

Тесты: `src/lib/imageCompression.test.ts`, 27 проверок. Canvas в jsdom нет,
поэтому пути с реальным кодированием проверяются через подмену `getContext`
и `toBlob`, а не через настоящий растр.

### 34.4 Не проверено вживую

Сжатие не проверено кликом на настоящем телефоне: нужно снять страницу
тетради, сдать её и убедиться, что рукописный текст читается при увеличении
и что рамки ИИ-проверки ложатся по строкам. Если окажется мелко — поднимать
`maxDimension` у `HOMEWORK_PHOTO_PRESET`, это одна константа.

### 34.5 Хвост

`VITE_ASSETS_BASE_URL` задана только в переменных окружения Vercel. В локальном
`.env` её не было, и пока в Supabase лежала копия каталога, это было незаметно:
`getAssetUrl` молча откатывался на Supabase Storage. Теперь откатываться некуда,
и без этой строки при `npm run dev` каталог будет без картинок.

## §35. Сдача ДЗ была сломана в проде, два бесконечных цикла, каркас интерфейса (2026-08-01)

### 35.1 Главное: ученик не мог приложить файл к ДЗ

`TopicHomeworkStudent` брал из хука `uploadAttemptFiles` — множественную загрузку
с прогрессом по каждому файлу. В `useTopicHomework` такой функции не было, там
осталась одиночная `uploadAttemptFile`. Обе половины закоммичены в `main`:
компонент обновили, хук — нет. В продакшене ученик, нажимая «прикрепить файл»,
получал `uploadAttemptFiles is not a function`.

**Почему это не поймали — важнее самой поломки.** В `vercel.json` командой сборки
стояло `npx vite build`. Vite типы не проверяет, он их просто вырезает, поэтому
ошибка типов деплой не остановила. А тесты компонента мокают хук целиком и о
расхождении не знают по определению. То есть у расхождения «компонент ↔ хук» не
было ни одной преграды на пути в прод.

Починка: написана `uploadAttemptFiles(attemptId, files, onProgress)` — файлы
идут по очереди (ученик сдаёт с телефона, пять параллельных отправок на слабом
канале мешают друг другу и врут в прогрессе), позиции продолжают уже приложенные
страницы. Раньше в одиночной версии стоял жёсткий `position: 0` — при
докладывании файлов порядок страниц в проверке разъехался бы, и рамки ИИ легли
бы не на ту страницу. Старая одиночная оставлена тонкой обёрткой.

**Команда сборки на Vercel заменена на `npm run build`** (то есть `tsc -b && vite
build`). Это стало возможно только после того, как все 26 ошибок типов были
разобраны (§35.3). Если сборка снова обрастёт ошибками, чинить их надо сразу:
как только команду откатят обратно на `vite build`, этот класс поломок вернётся.

### 35.2 Два бесконечных цикла перерисовки

**`CourseProgramPage`.** Объект `homeworkByTopic` собирался через `reduce` прямо
в теле рендера — новый объект на каждую перерисовку. Рядом стоял эффект с этим
объектом в зависимостях, а внутри — `setState`. Дальше по кругу: рендер → новая
ссылка → эффект → `setState` → рендер. React обрывает такое после пятидесяти
вложенных обновлений ошибкой «Maximum update depth exceeded» и **выбрасывает
вместе с ним всё отложенное обновление**, включая переход на другую страницу.

Снаружи это выглядело так: адрес в браузере сменился (историю роутер меняет
сразу), а дерево так и не закоммитилось — на экране осталась прежняя страница.
Владелец жил с этим неделю, описывая как «нажимаю, ссылка меняется, а страница
нет, надо жать кружок». Диагноз, который не сработал: сначала грешили на
чанки и вкладки, открытые до деплоя (Skew Protection). Версия развалилась о факт,
что воспроизводится и на локальном сервере. Нашлось по консоли: 4800 одинаковых
ошибок React за секунду.

**`useStudentJournal`.** В зависимостях эффекта стоял сам объект `profile`. В
проде не стреляло — в `App.tsx` есть защита `profilesEqual`, не переписывающая
профиль в сторе без изменений. Но в тестах цикл был, и прогон захлёбывался тем же
потоком ошибок, на который никто не смотрел, потому что проверки проходили.
Зависимость заменена на `profile?.id`.

**Правило на будущее.** Значение, которое пересоздаётся на каждый рендер (объект,
массив, результат `map`/`reduce`), не должно попадать в зависимости эффекта с
`setState` внутри. Либо `useMemo`, либо — лучше — не класть производную величину
в состояние вовсе, а считать на месте. Сканер по этому шаблону прогнан по всему
`src`: больше таких мест нет. Ложные срабатывания дал правильный приём —
зависимость собирают в строку (`attempts.map(a => a.id).sort().join(',')`), она
сравнивается по значению.

### 35.3 Разбор 26 ошибок типов

Сгенерированные типы Supabase отставали: в `database.ts` не было ни
`topic_homework_ai_jobs`, ни `topic_homework_ai_findings`, ни функции
`topic_homework_ai_mark_accepted` — их добавили миграциями 30 июля, а типы после
этого не перегенерировали. Перегенерированы через MCP; заодно появилась колонка
`attempt_id` у `annotation_sets`.

`LessonHomeworkV2Card` запрашивал колонку `homework_templates.lesson_id`, которой
в базе нет и не было. Контур Homework V2 мёртв (0 строк), карточка не работала
и в рантайме — удалена вместе со страницы урока и своими тестами по решению
владельца.

Остальное — мелочи: пропс `title` у `SignedFileLink`, недостающие поля в тестовых
фикстурах (`due_at`, `grade_scale`, `score`, `section`), сужение union-типа
пропсов в тестах `SubmissionReviewer`.

### 35.4 Каркас интерфейса

Шапка приведена к одной строке: подпись «Быстрый доступ через навигацию слева»
ничего не сообщала, а иконка лупы рядом читалась как поиск, которого нет. Список
`PAGE_TITLES` был неполным — «Программа курса», «Тесты», «Ученики» и все
ученические страницы показывали в шапке техническое «School OS»; добавлены все
живые маршруты из `AppRoutes`.

Двойные отступы убраны в 19 страницах. Каркас задавал рамку, и поверх неё каждая
страница добавляла свои `px-4 py-8` — в сумме 64 пикселя пустоты под шапкой и 48
по бокам. Теперь рамку задаёт только каркас, страницы отвечают за ширину и
внутренние промежутки.

В боковом меню разведены одинаковые иконки: у преподавателя «Кабинет учителя» и
«Программа курса» стояли с одним значком книги, у администратора «Панель админа»
и «Настройки» — с одной шестерёнкой. Когда значки повторяются, пункт приходится
читать, а не узнавать.

### 35.5 Каталог: скелет только на месте списка

При переключении темы страница подменялась скелетом целиком — пропадали
хлебные крошки, левый список тем и фильтры, то есть ровно то, что не менялось.
Четыре секунды такого экрана читаются как поломка. Теперь заглушка стоит только
на месте карточек задач; то же на странице раздела.

Убрана подпись «Наведи курсор сюда, чтобы крутить каталог»: если элементу нужна
инструкция, чинить надо элемент.

### 35.6 Курсы — карточки-ссылки, выбор живёт в адресе

Список курсов слева заменён на сетку карточек. **Карточка — `<Link>`, а не
`<button>`**, и это главное решение: обычный клик проваливает в курс на весь
экран, Ctrl+клик и клик колёсиком открывают его в новой вкладке браузера, адрес
видно в статусной строке и можно скопировать. С кнопкой не работает ничего из
этого.

Чтобы ссылки заработали, выбранный курс и активная вкладка переведены из
`useState` в адрес. Раньше они хранились дважды и синхронизировались двумя
эффектами — той самой конструкцией, в которой жил цикл из §35.2. Оба эффекта
удалены, состояние выводится из `searchParams`. Источник поломки исчез как класс,
а не был заклеен.

Архивные курсы свёрнуты под спойлер «Архив · N»: три технических «[E2E] Цикл ДЗ …»
оттесняли рабочие курсы за первый экран.

У вкладок курса появились `role="tablist"` / `role="tab"` / `aria-selected` —
скринридер объявляет «вкладка 3 из 6», а не просто «кнопка». Три теста этого
ждали и падали.

### 35.7 Кабинеты не падают в белый экран

`StudentDashboard` разваливался на `stats.hwRevision`, `TeacherDashboard` — на
`pendingReviews.length`, если хук вернул неполные данные. Это первый экран после
входа, падать ему нельзя: сбой запроса или отвалившийся RLS давали белый экран
вместо кабинета. Добавлены безопасные значения по умолчанию.

### 35.8 Что не проверено вживую

- сдача ДЗ файлом после починки — **обязательно проверить, это была реальная
  поломка в проде**;
- сжатие на настоящем телефоне: читается ли рукописный текст при увеличении и
  ложатся ли рамки ИИ по строкам. Если мелко — поднимать `maxDimension` у
  `HOMEWORK_PHOTO_PRESET`, это одна константа;
- перестроенный раздел курсов, особенно Ctrl+клик по карточке;
- 19 страниц с изменёнными отступами — механическая правка, но затрагивает всё.

### 35.9 Хвосты

- **12 красных тестов, все старые.** Девять — моки кабинетов, отставшие от формы
  данных; после §35.7 они уже не падают на рендере, но проверяют содержимое,
  которого хук не возвращает. Три — подсказка про группы, баннер ошибки
  материалов и «В теме N домашних заданий» из легаси-таблицы `homeworks`.
  Красный блок мешает замечать настоящие поломки — сегодня на этом и обожглись.
- **Skew Protection на Vercel** по-прежнему не включён (хвост из §27.5). К
  «адрес меняется, страница нет» он отношения не имел, но свой класс проблем со
  вкладками, открытыми до деплоя, лечит.
- Полный `npx vitest run` на машине владельца съедает больше 4 ГБ и роняет
  воркеры — гонять `npm run test:half1` и `test:half2`.

## §36. Копирование курса и темы (2026-08-01)

### 36.1 Зачем и что переносится

Каждый учебный год курс собирается заново, хотя от прошлого отличается
десятком дат. Теперь курс копируется целиком, а отдельная тема — в любой
другой курс: тему девятого класса можно перенести в одиннадцатый одной
кнопкой, оригинал при этом остаётся на месте.

Переносится: модули и темы, все материалы (включая скрытые), домашние задания
вместе с приложенными файлами, привязки к тестам. Не переносится: ученики,
заявки на вступление, сданные работы и оценки. Ссылка-приглашение у копии своя
— она создаётся заново вместе с курсом, старая на копию не ведёт.

Копия курса создаётся черновиком (`is_draft = true, is_active = false`), а
домашние задания в ней — неопубликованными. Полуготовый курс, случайно
показанный ученикам, стоит дороже лишнего клика на публикацию.

### 36.2 Три фазы, а не одна RPC

Файлы материалов лежат в Storage, и скопировать объект изнутри Postgres нельзя.
Поэтому операция разбита на три шага, по образцу уже существовавшего
`stage_lesson_copy`:

1. **stage** — `course_copy_stage` / `topic_copy_stage` создаёт курс или тему со
   всем наполнением, заводит строку в `course_copy_jobs` и возвращает список
   объектов, которые надо продублировать;
2. **copy** — клиент (`src/lib/courseCopy.ts`) копирует объекты внутри
   хранилища через `storage.copy`, по одному: батч-копирования нет, а
   параллельный залп на десятках файлов ловит 429;
3. **finalize** — `course_copy_finalize` закрывает задание. Если вторая фаза
   сорвалась, вызывается `course_copy_rollback`.

**Откат обязателен.** Курс со ссылками на несуществующие файлы хуже, чем
отсутствие копии: преподаватель считает материалы на месте и обнаруживает
пустоту на уроке. Откат делается best-effort, и если не прошёл он сам —
показывается исходная ошибка, она полезнее.

**Пути новых объектов строит база**, в виде `<newTopicId>/<uuid>-<basename>`.
Это не косметика: RLS на `storage.objects` разбирает первый сегмент пути как id
темы. Путь другого вида молча лишит преподавателя доступа к его же файлам.

### 36.3 Даты спрашиваются, а не угадываются

Три режима: очистить, оставить как есть, сдвинуть. Сдвиг задаётся **новой
датой, а не числом дней** — преподаватель знает, что курс стартует 1 сентября,
а не что его надо сдвинуть на 358 дней. Число считается из двух дат
(`shiftDaysBetween`) и показывается подписью.

Счёт идёт в UTC-полночи. По локальному времени переход на зимнее время даёт
сутки длиной 25 часов, деление на 24 — дробь, и округление уезжает на день.
На это есть тест.

Если у оригинала не заполнена опорная дата (`start_date` у курса,
`available_from` у темы), режим «сдвинуть» отключён: сдвигать не от чего.

### 36.4 Права

`course_copy_stage` — только владелец курса или админ. `topic_copy_stage`
требует одновременно `topic_material_can_manage` на исходной теме и
`course_is_staff` на курсе назначения: копировать можно только то, к чему есть
доступ, и только туда, куда есть доступ. `course_copy_topic_content` отозвана у
`authenticated` — она внутренняя. Задания в `course_copy_jobs` видны и
закрываются только своим автором.

Миграция `20260801154048_course_and_topic_copy` перед применением прогнана
локально на Postgres 16 под `set role authenticated` — 15 проверок поведения,
включая отказы по правам.

### 36.5 Интерфейс

Точки входа: кнопка «Скопировать курс» на вкладке «Настройки» курса и иконка
копирования в строке темы, рядом с «Редактировать тему».

Оба диалога делят `copyDialogParts.tsx`: рамку окна, выбор режима дат, полосу
прогресса и текст «что перенесётся, что нет». Вынесено не ради экономии строк,
а чтобы оба окна говорили о датах одними словами: для преподавателя это одна
операция, и разные формулировки читаются как разные вещи.

Прогресс показывается счётчиком «N из M», а не крутилкой: файлов у курса бывают
десятки, копируются по одному, и без числа это выглядит как зависание. Во время
копирования окно не закрывается ни по фону, ни по Esc.

**`loadModules` в диалоге темы держится в ref.** Функция приходит из хука и
пересоздаётся на каждый рендер; в зависимостях эффекта с `setState` внутри это
ровно тот замкнутый круг из §35.2, который ломал переходы между страницами.
Эффект зависит от id курса, функция берётся из ref. Там же защита от гонки:
при быстром переключении курсов ответ по старому курсу не должен перезаписать
список нового.

### 36.6 Что не проверено вживую

Ни одна копия ещё не сделана на боевом. Проверить в таком порядке:

- копия курса с материалами и файлами — открываются ли файлы в копии (это
  главная проверка: если пути собраны неверно, RLS откажет молча);
- копия темы в другой курс — та же проверка файлов;
- режим «сдвинуть»: сдвинулись ли сроки ДЗ, а не только дата старта;
- сорванное копирование: отключить сеть на середине и убедиться, что откат
  убрал полуготовый курс.

### 36.7 Хвост

Общие `Input` и `Select` не связывают подпись с полем через `htmlFor`/`id` —
скринридер поле не называет, а в тестах приходится искать через обёртку.
Чинится одним `useId` в двух примитивах, но затрагивает все формы, поэтому
отложено.
