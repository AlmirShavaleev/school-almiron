# School: повторное использование планов внутренних чтений

Причина: новый браузерный прогон выдержал ступень 10 активных учеников без 5xx, на 15 появились задержки и ошибки, на 20 тест остановился. Журналы показывали отмены во время запуска внутренних функций.

В отдельном свежем EXPLAIN тело student_exam_evidence_rows потратило 245,303 мс на планирование и 133,931 мс на выполнение с инструментированием. Это не задержка API и не постоянная характеристика: холодные вызовы сильно колеблются.

## Применено в School

- `20261116234836_cache_inner_read_query_plans`
- `20261116235403_reuse_generic_plans_for_inner_reads`

Четыре внутренние функции переведены с LANGUAGE sql на PL/pgSQL со статическим RETURN QUERY / RETURN. Сам SELECT сохранён. Возвращаемые поля явно приведены к прежним объявленным типам:
- student_exam_evidence_rows;
- student_solved_task_days;
- _progress_state;
- progress_open_by_student.

Для этих четырёх функций задан plan_cache_mode=force_generic_plan. Это настройка функции, а не БД, роли или сессии клиента. После возврата исходная настройка вызывающего восстанавливается. Для пустых фильтров progress_open_by_student прежний пустой объект возвращается до подготовки большого запроса.

Кешируется план запроса, а не результат. Следующий вызов читает актуальные данные. Сигнатуры, владельцы, ACL, STABLE, SECURITY DEFINER/INVOKER и search_path сохранены. Новых доступных клиенту функций нет.

Механизм подготовленных планов описан в [документации PostgreSQL 17](https://www.postgresql.org/docs/17/plpgsql-implementation.html#PLPGSQL-PLAN-CACHING). В School используется PostgreSQL 17.6. SQL-функции старого механизма повторно планировались в следующих внешних запросах; контекст изменения механизма описан в [коммите PostgreSQL](https://www.postgresql.org/message-id/E1u02Tn-002Kp0-0Q@gemulon.postgresql.org).

## Проверки

- Сохранены исходные определения и результаты для всех 98 профилей.
- После замены функций и после отдельной настройки планирования совпали контрольные суммы всех четырёх результатов для 98 профилей. _progress_state дополнительно проверялся на реальном курсе из 108 тем для соответствующего student_id каждого профиля.
- Под authenticated успешно вызваны публичные прогноз и активность для ученика, постороннего преподавателя и отсутствующего профиля.
- Владельцы и ACL четырёх функций совпали с исходными. Прямой вызов внутренних функций браузерной ролью не разрешён.
- Категории и количество замечаний Supabase после изменений не изменились.
- Локально прошли 67 тестов в 5 наборах и проверка типов.
- Новые тесты используют настоящие SQL-запросы и проверяют источники ДЗ, тестов, пробников, каталога и вариантов; веса; дедупликацию решённых задач; смену учеников и дат после повторных вызовов; прогресс и демо; новые данные после прогрева; пустые фильтры; отсутствие расширения прав; восстановление настройки вызывающего.

## Замеры

По 7 последовательных динамических внешних SELECT до и после, в read-only транзакциях. Первый вызов исключён; таблица показывает медиану оставшихся 6. Это имитирует новые внешние запросы на одном соединении, а не повтор одного вызова внутри одного SQL-оператора.

| Внутренняя функция | До | После |
|---|---:|---:|
| student_exam_evidence_rows | 9,219 мс | 1,571 мс |
| student_solved_task_days | 2,952 мс | 0,790 мс |
| _progress_state | 8,012 мс | 4,441 мс |
| progress_open_by_student | 0,676 мс | 0,145 мс |

Первые вызовы всё ещё требуют построения плана. Результаты зависят от соединения, данных и нагрузки. Это не замер HTTP, страницы или нового предела одновременных учеников.

Сценарий следующего сравнения: тот же мобильный нагрузочный тест, те же аккаунты и ступени 1/3/5/10/15/20. Проверять P95, ошибки экранов и 5xx, а не только среднее.

## Откат

rollback_school_inner_plans.sql восстанавливает прежние определения и снимает настройку планирования. При необходимости применять как новую миграцию после проверки актуального состояния. Историю двух применённых миграций не удалять. Остальные этапы оптимизации сохраняются.

Нагрузочный тест рабочей БД в этой работе не запускался; клиентские запросы и пользовательские данные не менялись.
