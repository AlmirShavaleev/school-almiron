### 2. Гейт «Решения ДЗ» — решение владельца, самое важное

Ученик видит рубрику «Решение ДЗ» ТОЛЬКО если его попытка по ДЗ этой
темы **принята** (accepted). Не сдал или на доработке — не видит
никогда. Преподаватель/куратор видят всегда.

**Гейт обязан держаться на сервере, не в клиенте:** спрятанная в UI
рубрика, чей файл достаётся прямым запросом к Storage/таблице, — это не
гейт. Разберись, как ученик сейчас получает материалы (RLS
topic_materials/topic_material_items + подписанные ссылки) и поставь
условие «есть accepted-попытка по ДЗ темы» в серверную проверку для
рубрики решения. Отказ — пустой список рубрики, это нормальный случай
(не ошибка). Клиент дополнительно показывает ученику плашку «Решение
откроется после принятия твоего ДЗ» — чтобы рубрика не выглядела
пропавшей.

Ловушка из уроков проекта: правило «видит/не видит» держи в ОДНОЙ
серверной функции/политике; клиентская проверка — только косметика
поверх (рассинхрон копий — §21/§29).

### 3. UX модалки ДЗ и загрузок (жалобы владельца по скриншотам)

- **Превью вложений.** Прикреплённый скриншот/картинка в списках
  вложений (модалка ДЗ, конспект, все рубрики) показывается строкой
  «скриншот-1.png (74 КБ)». Нужна миниатюра-превью у картинок — у тебя
  уже есть `SignedImage` (§81), используй его маленьким тумбом; PDF
  остаётся строкой с иконкой. Клик по тумбу — открыть оригинал.
- **Публикация ДЗ.** Бейдж-переключатель «Опубликовано ⇄ Черновик»
  (§75) владельцу неудобен: «надо нажать на черновик, и она только
  потом опубликуется». Переделать: внизу модалки явная кнопка
  **«Опубликовать»** (для черновика) / «Снять с публикации» (для
  опубликованного), бейдж остаётся индикатором, НЕ кнопкой. После
  нажатия «Опубликовать» — сразу раскрыть аккордеон «Оповестить в
  Telegram» (§75) как следующий шаг: опубликовал → предложило
  оповестить. Отдельную модалку городить не нужно — аккордеон уже есть.

## Порядок

1. Сначала короткий план оркестратору: где живёт список рубрик (enum?
   константа? строки в БД?), как ляжет гейт решения (какая
   политика/функция), что с копированием курса (новые рубрики должны
   переживать копирование — правило §59: nullif-логику тумблера тем не
   зацепи). Потом код.
2. Миграции — только MCP `apply_migration` + файл с точным именем;
   правки схемы → перегенерация типов MCP (руками не дописывать — урок
   §75, уже в правилах).
3. Гейт проверить пробами под set role authenticated: ученик без
   попытки / с returned / с accepted; отказ виден как пустота рубрики —
   для ЭТОГО случая пустота и есть контракт, зафиксируй это в пробе
   осознанно (отличие от урока §54 — там пустота маскировала ошибку).
4. Номер — хвост+1 в момент записи; полный tsc ПОСЛЕДНИМ действием
   перед отчётом (урок §89: tsc в середине работы пропустил поломку).
5. Копирование курса и шаблоны уроков — проверь, что новые рубрики в
   них живут; `git status` до и после; отчёт оркестратору.
